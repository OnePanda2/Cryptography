## 1. Protocols

### 1.1 TLS

**TLS 1.3** (RFC 8446, 2018) is the current standard, the result of a multi-year, unusually open design process that removed a long list of historically-exploited legacy features present in TLS 1.2 and earlier: static RSA key exchange (no forward secrecy — a compromised long-term key retroactively decrypts all past traffic, exactly the confidentiality property PQC's "harvest-now-decrypt-later" concern generalizes), CBC-mode ciphersuites (source of the Lucky13/POODLE/BEAST padding-oracle-adjacent attack family), RC4 (Part 2), compression (source of the CRIME/BREACH side-channel-via-compression-ratio attacks), and renegotiation-related vulnerabilities. TLS 1.3 mandates **forward secrecy** for every handshake (via ephemeral (EC)DH, now transitioning to hybrid PQC per Part 3), reduces the handshake to one round trip (1-RTT, with an optional 0-RTT mode carrying its own, explicitly documented replay-risk caveats that protocol designers must handle deliberately), and formally verified core handshake properties via multiple independent academic analyses (Tamarin-prover and ProVerif-based formal verification efforts ran *alongside* the standardization process itself, an unusually rigorous practice compared to most prior protocol standardization).

The **post-quantum hybrid rollout** (Part 3, 2.4) is happening entirely within the TLS 1.3 `key_share` extension mechanism — hybrid groups like X25519MLKEM768 are just new entries in the existing `supported_groups`/`key_share` negotiation, requiring no protocol-version change, which is precisely why the rollout has been able to proceed as a relatively low-friction, incremental deployment (client and server support the new group; if either side lacks it, they fall back to a classical group) rather than a disruptive TLS 2.0-style break.

### 1.2 Noise Protocol Framework

**Noise** (Trevor Perrin) is not a single protocol but a **framework** for building custom Diffie-Hellman-based handshake protocols from a small set of composable message patterns (documented as `Noise_XX`, `Noise_IK`, `Noise_NK`, and many others, each pattern specifying exactly which keys are known/exchanged/authenticated at each step). Its value proposition is precisely that hand-rolling a secure handshake protocol from scratch is extremely error-prone (see the historical TLS vulnerability list above), so Noise gives protocol designers a small, well-analyzed vocabulary of secure patterns to select and compose rather than inventing new ones. **WireGuard** (1.6 below) is built directly on a specific Noise pattern (`Noise_IK`, roughly), and Noise's influence is visible across a wide range of newer protocol designs precisely because it lets a small team ship a custom secure-transport protocol without redoing the formal-analysis work TLS required.

### 1.3 SSH

The SSH protocol (RFC 4251-4254 and successors) predates TLS 1.3's design lessons but converged on broadly similar practice over time: modern SSH implementations (OpenSSH being the dominant one) default to Curve25519-based key exchange (`curve25519-sha256`), Ed25519 host/user keys, and ChaCha20-Poly1305 or AES-GCM for the transport cipher — essentially the same primitive choices TLS 1.3 and Signal converged on, a genuinely notable point of cross-protocol consensus given the three ecosystems' largely independent design histories. Post-quantum hybrid key exchange for SSH (combining classical ECDH with ML-KEM) is under active IETF standardization and already available in current OpenSSH releases as an opt-in/negotiated option, following the TLS hybrid rollout by roughly a year or two.

### 1.4 Signal Protocol and secure messaging

Covered in depth because it is widely regarded (including by NIST's own PQC conference presentations, per Part 3's search record) as the reference design for modern asynchronous secure messaging:

- **X3DH** (Extended Triple Diffie-Hellman, Marlinspike/Perrin, 2016): establishes an initial shared secret between two parties who may not both be online simultaneously (a structural requirement mobile messaging imposes that real-time protocols like TLS don't face), using a combination of each party's long-term identity key, a signed prekey (refreshed periodically, signed by the identity key), and one of many pre-published one-time prekeys — allowing Bob to receive an authenticated, forward-secret initial message from Alice even if Bob is offline when Alice sends it, by having Bob pre-publish key material to a server in advance.
- **Double Ratchet** (Marlinspike/Perrin, building on earlier "Axolotl" work): provides ongoing per-message key evolution combining a **DH ratchet** (a fresh DH exchange performed roughly once per round-trip of the conversation, providing **post-compromise security** — if a party's state is compromised, the *next* DH ratchet step heals the compromise for future messages) with a **symmetric-key ratchet** (a one-way hash-chain derivation for each individual message within a DH ratchet step, providing **forward secrecy** — compromising the current chain key doesn't reveal past message keys, because the derivation is one-way). The formal security notions here (Alwen–Coretti–Dodis and related academic work formalizing exactly what "Double Ratchet" security means) are themselves an important piece of the applied-provable-security literature, not just an engineering artifact.
- **PQXDH** (2023): replaces X3DH's pure-ECDH initial handshake with a **hybrid** combining classical X25519 with ML-KEM (then still called Kyber, pre-FIPS-203-naming), specifically to defend the *initial* key agreement against harvest-now-decrypt-later. Deployed across Signal in 2023, ahead of the formal NIST FIPS finalization — Signal's engineering team made a deliberate, publicly-explained choice to deploy pre-standardization Kyber given the urgency of the HNDL threat model for long-lived conversation confidentiality, accepting some algorithm-agility risk in exchange for earlier protection.
- **Triple Ratchet / SPQR (Sparse Post-Quantum Ratchet)** (2025): recognized that PQXDH alone only protects the *initial* handshake — if a party's ongoing Double Ratchet state is later compromised, subsequent messages remain vulnerable to HNDL via the classical-ECDH-based ratchet steps, even though the initial handshake was PQC-hybrid-protected. SPQR adds a **second, parallel post-quantum ratchet** (using ML-KEM, chunked via erasure coding to handle its much larger key/ciphertext sizes over an asynchronous, potentially-lossy transport, and choreographed via an explicit per-device state machine) running alongside the classical Double Ratchet; the two ratchets' outputs are mixed together, giving the combined "Triple Ratchet" continuous post-quantum forward secrecy and post-compromise security for the *entire* conversation lifecycle, not just the handshake. The design was published with formal security proofs at Eurocrypt 2025 (erasure-code-based chunking) and USENIX Security 2025 (a comparative analysis of six candidate post-quantum ratchet designs, from which SPQR and an alternative "Katana" KEM-based design emerged as the strongest options — Signal chose to ship the standards-based SPQR/ML-KEM approach first, explicitly noting Katana as a promising but non-standardized alternative for potential future work). Deployment includes cryptographically-authenticated graceful downgrade for mixed old/new client populations, specifically engineered to prevent an active attacker from forcing a downgrade to the weaker classical-only ratchet.
- **Apple's PQ3** (iMessage, shipped iOS 17.4, 2024): conceptually parallel to Signal's approach — Apple describes it as reaching "Level 3" post-quantum security specifically because it protects the *ongoing* ratchet, not just the initial handshake, predating Signal's Triple Ratchet by roughly a year and widely discussed alongside it as jointly defining the current state of the art for what "post-quantum secure messaging" actually requires (continuous protection, not just a PQC-protected handshake with a classical ongoing ratchet).

### 1.5 Key management, certificates, and PKI

**Public Key Infrastructure (PKI)** solves the problem X.509/TLS/most public-key deployments face: a public key alone doesn't tell you *whose* key it is. A **Certificate Authority (CA)** vouches for the binding between a public key and an identity by issuing a signed certificate; browsers/OSes ship a curated **root store** of trusted CAs, and certificate chains are verified up to a trusted root. Real, repeatedly-exploited weaknesses in this model have included: CA compromise (DigiNotar, 2011 — a compromised CA issued fraudulent certificates for high-value domains including Google properties, used in real surveillance/interception attacks against Iranian users, and the incident directly led to DigiNotar's removal from every major root store and the company's collapse); weak-hash-based certificate forgery (the 2008 MD5-collision rogue-CA demonstration, Part 2); and misissuance more generally, which motivated **Certificate Transparency** (Google-initiated, now an IETF/CA-Browser-Forum requirement) — a public, append-only, cryptographically-verifiable log of every issued certificate, so misissuance becomes detectable (any domain owner can monitor CT logs for unexpected certificates for their own domains) even when it can't be prevented outright at issuance time.

### 1.6 WebAuthn, Passkeys, and FIDO2

**FIDO2** (combining the **WebAuthn** W3C browser API standard with the **CTAP** client-to-authenticator protocol) is the modern standard for public-key-based authentication replacing passwords: a user's device generates a fresh public/private key pair *per relying party* (per website), keeps the private key non-exportable (ideally in a hardware secure element/TPM), and the website stores only the public key — meaning a server-side database breach leaks no secret credential material usable to impersonate users elsewhere (a direct, structural fix to the industry's endemic password-reuse-driven credential-stuffing problem, not merely a stronger password). **Passkeys** is the current consumer-facing branding for FIDO2 credentials with an added **synchronization** capability (via platform-provider cloud services — iCloud Keychain, Google Password Manager, etc. — using their own end-to-end-encrypted sync mechanisms) specifically to solve FIDO2's original device-loss usability problem (a hardware security key or device-bound credential, if the only copy, is unrecoverable if lost; synced passkeys trade a small amount of the strongest possible non-exportability guarantee for dramatically better mainstream usability, an explicit, debated design tradeoff within the FIDO Alliance's own standardization discussions).

### 1.7 OAuth

**OAuth 2.0** (RFC 6749 and its substantial ecosystem of extension RFCs) is an **authorization** delegation protocol — it lets a user grant a third-party application limited access to their resources on another service without sharing their actual credentials with that third party — and is frequently, incorrectly, conflated with *authentication*; **OpenID Connect** is the identity/authentication layer explicitly built on top of OAuth 2.0 to address exactly that gap, and the historical conflation of the two (using bare OAuth as if it were an authentication protocol) has been the source of real, documented vulnerability classes in web applications that rolled their own "login with X" flows without the OIDC layer's explicit identity-token guarantees.

## 2. Implementation Security

### 2.1 Constant-time programming

The discipline of writing cryptographic code whose execution time (and, ideally, memory-access pattern, and power consumption) is **independent of secret data** — directly defending against the timing and cache-timing attacks of Part 4, 1.5. Practical techniques: avoid secret-dependent branches (`if (secret_bit) { ... }` is dangerous; use branchless bit-masking/selection instead); avoid secret-dependent array indices (a lookup table indexed by secret data leaks via cache-timing regardless of branching); use fixed-iteration-count loops rather than early-exit on a secret condition; use dedicated constant-time comparison functions for anything comparing secret values (MAC tags, decrypted padding) rather than a language's default (often early-exit) comparison operator or `==`. This is genuinely hard to get right and even harder to *verify* is right, because compilers are not obligated to preserve "constant-time-ness" — an optimizing compiler can legally transform branchless, constant-time-looking source code into branching machine code if it judges that equivalent under the language's ordinary (non-security-aware) semantics, a real, recurring problem that has motivated dedicated tooling (see 2.4) and, in some cases, hand-written assembly for the most security-critical inner loops of widely-used libraries.

### 2.2 Memory safety and language choice

A large fraction of historically catastrophic cryptographic-library vulnerabilities (Heartbleed being the most famous — a 2014 OpenSSL buffer over-read in the TLS heartbeat extension that let an attacker read arbitrary adjacent heap memory, including private keys, from a huge fraction of the internet's TLS servers) were **memory-safety** bugs, not cryptographic-algorithm flaws — a distinction worth being explicit about, since "cryptography vulnerability" headlines very often actually describe ordinary C memory-safety bugs that happen to occur in cryptographic code, not any weakness in the underlying mathematics. This has driven a real, ongoing industry shift:
- **C** remains dominant in legacy cryptographic libraries (OpenSSL) for historical/compatibility/performance reasons, but requires extraordinary discipline (and, per the Debian OpenSSL and Heartbleed histories, has repeatedly failed to receive it in practice at scale) to avoid buffer overflows, use-after-free, and related memory-safety bugs, on top of the constant-time discipline above.
- **Rust**'s ownership/borrow-checker model provides compile-time memory safety guarantees (no use-after-free, no buffer overflows, no data races) without a garbage collector's runtime cost, making it increasingly the language of choice for new cryptographic implementations where performance matters (examples across the ecosystem include RustCrypto's primitive implementations and multiple newer TLS-stack efforts) — though Rust's guarantees don't automatically extend to `unsafe` blocks (sometimes still needed for genuinely low-level operations) or to timing-side-channel-freedom (a separate property the type system doesn't enforce).
- **Undefined behavior (UB)** in C/C++ specifically is a recurring, subtle source of security-relevant miscompilation: code that appears to correctly zero out a sensitive buffer after use (`memset(secret_buf, 0, len)`) can be legally eliminated entirely by an optimizing compiler if it can prove the buffer is never read again — the buffer holding the secret key material *remains in memory* despite the source code appearing to clear it, a real, historically-documented class of bug that motivated dedicated "secure memzero" library functions (with compiler-visible side effects specifically to prevent this optimization) across essentially every serious cryptographic library.

### 2.3 Secure coding and side-channel-aware development practice

Beyond constant time and memory safety specifically: minimizing the amount of code that touches raw key material at all (isolating it behind narrow, audited interfaces); zeroing sensitive memory after use (with the UB caveat above in mind); avoiding secret material in swap-able memory where possible (`mlock`/`VirtualLock`-family APIs); and defensive-by-default API design (making the *easy*, obvious way to use a cryptographic library also the *safe* way — libsodium's design philosophy explicitly, per 3.6 below — rather than exposing low-level primitives that are easy to misuse, which was historically OpenSSL's more criticized design posture before its own API modernization efforts).

### 2.4 Formal verification, testing, and fuzzing

- **Formal verification**: tools like the **Tamarin prover** and **ProVerif** allow mathematically proving protocol-level security properties (secrecy, authentication, forward secrecy) against a symbolic (Dolev-Yao-style) attacker model, and were used *during*, not just after, TLS 1.3's design process — a genuinely notable and increasingly-expected practice for any new protocol design of comparable stakes; **CryptoVerif** and related tools push toward *computational* (not just symbolic) formal guarantees, closer to the reduction-based proofs of Part 1. At the implementation level, tools like **HACL\*** (a formally-verified cryptographic library, written in F* and compiled to C, used inside Mozilla's NSS and other production TLS stacks) go further still, formally verifying that the *actual compiled code*, not just an abstract protocol description, meets both functional correctness and — critically — constant-time-execution properties simultaneously, directly addressing the 2.1 compiler-transformation concern via verification of the generated code itself rather than just the source.
- **Fuzzing**: automated, coverage-guided random/mutational input generation (AFL, libFuzzer, and OSS-Fuzz's continuous, large-scale application of these tools across major open-source cryptographic libraries) has found a substantial number of real memory-safety and parsing bugs in widely-deployed cryptographic code (OpenSSL, BoringSSL, and others are all continuously fuzzed as standard practice today, a direct, structural response to the Heartbleed-era realization that this class of code had received insufficient adversarial testing relative to its stakes).
- **Side-channel-specific testing tools**: beyond general fuzzing, dedicated tools exist specifically to detect *timing* variation correlated with secret inputs — **dudect**-style statistical timing-leakage detection, and more recent systematic tooling applied specifically to the new NIST PQC signature candidates (timing-leakage analysis of PQDSS candidates has been an active, published research area through 2025, directly relevant to catching exactly the kind of Falcon/FN-DSA Gaussian-sampling side-channel risk flagged in Part 3).

## 3. Real-World Systems

### 3.1 Blockchain and cryptocurrency systems

- **Bitcoin**: secp256k1 ECDSA for transaction signatures, SHA-256 (double-hashed) for proof-of-work and transaction/block hashing. Its cryptography is deliberately conservative and has not needed to change since 2009; the live research/engineering conversation is entirely about its **future** PQC migration path (a genuinely hard problem for Bitcoin specifically, because address reuse means many historical public keys are already exposed on-chain, making a clean "just swap the signature algorithm" migration much harder than for systems where public keys aren't permanently, publicly recorded — an actively-debated topic within the Bitcoin developer community, referenced directly in the 2026 Anthropic/HAWK coverage discussed in Part 3).
- **Ethereum**: secp256k1 for account signatures; increasingly BLS signature aggregation (Part 3, 1.5) for validator consensus messages in its proof-of-stake design, plus extremely heavy use of zk-SNARK/zk-STARK-based **rollups** (Layer-2 scaling systems that batch many transactions off-chain and post a succinct cryptographic proof of their correctness on-chain) as the dominant real-world production application of the zero-knowledge-proofs research program covered in Part 6.
- **Zcash**: pioneered production-grade **zk-SNARKs** for fully shielded (amount- and participant-hiding) transactions, using a Groth16-family proving system historically requiring a trusted setup ceremony (mitigated via elaborate multi-party "powers of tau"-style ceremonies designed so the setup remains secure as long as at least one participant honestly destroys their secret contribution) — the standing real-world case study for both the power and the trusted-setup cost of pairing-based zk-SNARK systems, and a system that has continued actively evolving its PQC posture (a 2026 shielded-pool upgrade specifically designed for post-quantum recoverability was referenced directly in the Anthropic/HAWK coverage's search record, underscoring that privacy-coin ecosystems are treating quantum-readiness as an active, current engineering priority, not a someday concern).
- **Monero**: uses ring signatures (a signature scheme letting a signer prove membership in a group without revealing which member signed, providing sender ambiguity) combined with stealth addresses and confidential transactions (Pedersen-commitment-based amount hiding) for its privacy model — a structurally different cryptographic approach from Zcash's zk-SNARK model, worth knowing as a genuine architectural fork in how "privacy-preserving cryptocurrency" can be built.

### 3.2 Secure messaging and transport

- **Signal**: covered in full in 1.4 above.
- **Tor**: onion routing — messages are layered-encrypted (like an onion) with each relay's public key in sequence, so each hop can only decrypt its own layer, learning only the identity of the immediately-previous and immediately-next hop, never the full path — providing network-layer anonymity distinct from (and complementary to) the message-content confidentiality Signal-style protocols provide. Tor's own relay-to-relay circuit-establishment handshake (`ntor`, and its evolving successors) has itself gone through the same ECDH-hardening and, increasingly, PQC-hybridization progression documented for TLS/SSH/Signal above.
- **WireGuard**: a deliberately minimal (relative to IPsec's notorious complexity), Noise-Protocol-Framework-based VPN protocol using Curve25519, ChaCha20-Poly1305, and BLAKE2s exclusively — no algorithm negotiation/agility at the protocol level at all, a deliberate design choice by its author (Jason Donenfeld) explicitly trading long-term algorithm-agility flexibility for a dramatically smaller, more auditable, more analyzable codebase (WireGuard's entire cryptographic core is a small fraction of the size of comparable IPsec/OpenVPN implementations), on the philosophy that a small, fixed, expert-chosen primitive set that can be swapped out wholesale if ever needed is safer in practice than a large negotiable menu that inevitably accumulates weaker legacy options over time (exactly the failure mode that made TLS's pre-1.3 ciphersuite negotiation surface such a large historical attack surface).
- **Age**: a modern, deliberately simple file-encryption tool/format (Filippo Valsorda and Ben Cartwright-Cox; Valsorda's own later, separately notable public commentary on quantum timelines is referenced in Part 3) built on X25519, ChaCha20-Poly1305, and HMAC-based key derivation, explicitly positioned as a simpler, harder-to-misuse alternative to GPG for the common file-encryption use case, illustrating the same "small expert-curated primitive set beats a large flexible menu" philosophy WireGuard embodies, applied to file rather than transport encryption.
- **OpenSSH**: covered in 1.3.

### 3.3 Cryptographic libraries

- **libsodium** (a friendlier fork/wrapper around Daniel J. Bernstein's NaCl): explicitly designed around a "hard to misuse" API philosophy — high-level functions like `crypto_box` and `crypto_secretbox` bundle an entire correctly-composed AEAD construction (X25519 + XSalsa20 + Poly1305, or equivalent) behind a single function call with sane defaults, specifically to prevent the generic-composition and mode-selection errors documented across Parts 2 and this Part. Extremely widely used, audited, and trusted; a commonly-cited example of applied-cryptography API design done well.
- **OpenSSL**: the most widely deployed general-purpose cryptographic library in the world by installed base, with a long, complicated history including both genuine excellence (breadth of algorithm/protocol support, the library underlying a huge fraction of internet TLS) and serious documented failures (Heartbleed, the Debian entropy incident indirectly, and a historically criticized low-level API surface that made misuse easy) — currently undergoing sustained modernization (API improvements, the OpenSSL 3.x provider architecture, much heavier fuzzing investment) directly in response to this history.
- **BoringSSL**: Google's internal fork of OpenSSL, explicitly *not* intended for general external API-stability guarantees (Google has been unusually direct that other projects vendoring it should expect breaking changes), but highly influential as the codebase where a large share of the earliest production PQC-hybrid TLS experimentation (Kyber/ML-KEM hybrid groups) actually shipped first, per Part 3.
- **AWS-LC**: Amazon's own OpenSSL/BoringSSL-derived fork, FIPS-140-validated, and — per Part 3 — an early production shipper of ML-KEM behind its FIPS module boundary.

### 3.4 Hardware security

- **AWS KMS / Cloud HSM** and equivalent offerings from other major cloud providers: managed **Hardware Security Modules (HSMs)** — dedicated, tamper-resistant hardware devices that generate and store private keys such that the key material never leaves the device in plaintext, performing cryptographic operations (signing, decryption) internally and returning only results, specifically to defend against exactly the class of memory-disclosure and exfiltration risk that software-only key storage (even well-written software) cannot fully rule out.
- **Apple Secure Enclave**: a dedicated, isolated coprocessor (present in iPhones/iPads/Macs with Apple Silicon) with its own separate boot process, memory, and (where applicable) dedicated AES engine, specifically designed so that even a full compromise of the main OS kernel does not directly expose keys generated and held inside the Enclave — the underlying hardware trust anchor for iOS/macOS biometric authentication, Apple Pay, and (per Part 3) PQ3's key material handling.
- **TPM (Trusted Platform Module)**: an industry-standard (ISO/IEC 11889) dedicated security chip present in most modern PCs/servers, providing hardware-backed key storage, platform-integrity measurement/attestation (measuring boot-chain components into PCR registers, enabling remote attestation of a machine's boot state), and the hardware root of trust underlying full-disk-encryption key protection (BitLocker's TPM integration being the most visible consumer-facing example) and increasingly required as a baseline for modern OS security features (Windows 11's TPM 2.0 requirement being a direct, if debated, consequence).
- **Hardware wallets** (cryptocurrency-specific HSM-adjacent devices — Ledger, Trezor, and similar): apply the same "keys never leave the isolated hardware" principle specifically to cryptocurrency private key custody, with the device's small dedicated display and physical confirmation button existing specifically to defend against a compromised host computer silently substituting a different transaction than the one the user believes they're approving — a threat model (compromised host, trusted peripheral) directly analogous to the general HSM/Secure Enclave model above, just consumer-oriented.

### 3.5 How cryptography is actually deployed — the practitioner's summary

Across every system above, a consistent real-world pattern emerges, worth stating explicitly as this Part's synthesis: **deployed cryptographic security failures are overwhelmingly implementation, key-management, and protocol-composition failures, not algorithm-mathematics failures.** Heartbleed, the Debian entropy bug, DigiNotar, PS3/Android nonce reuse, Bleichenbacher-family padding oracles, Sweet32, and (per Part 4) essentially every side-channel attack ever published — none of these required a mathematical break of AES, RSA, or SHA-2/3. This is the single most important practical lesson the report's "real-world systems" survey supports, and it's exactly why Part 5's implementation-security material (2.1–2.4) and Part 4's randomness material carry equal or greater practical weight, for a working practitioner, than fluency in the mathematics of Part 1 alone.

## 4. Standards

| Body | Role | Key outputs relevant to this report |
|---|---|---|
| **NIST** (US) | Develops FIPS standards, runs open competitions (AES, SHA-3, PQC) | FIPS 197 (AES), FIPS 180-4/202 (SHA-2/3), FIPS 203/204/205/206 (PQC), SP 800-series guidance |
| **IETF** | Internet protocol standardization via open RFC process; **CFRG** (Crypto Forum Research Group) advises on algorithm choices for IETF protocols | RFC 8446 (TLS 1.3), RFC 8439 (ChaCha20-Poly1305), RFC 7748 (X25519/X448), draft-ietf-tls-mlkem and related PQC-hybrid drafts |
| **ISO/IEC** | International standardization (often harmonizing with/referencing NIST and national standards) | ISO/IEC 18033 (encryption algorithms), ISO/IEC 14888 (digital signatures), ISO/IEC 11889 (TPM) |
| **NSA** | Historically set US national-security cryptographic policy via **Suite B** (2005–2015-ish, a curated list of approved algorithms — AES, ECDH/ECDSA over NIST curves, SHA-2 — for protecting classified information up to certain levels); superseded by **CNSA 1.0** (2015) and now **CNSA 2.0** (2022-onward), which is explicitly the US national-security PQC migration mandate referenced throughout Part 3 | CNSA 2.0 algorithm suite and migration timeline |

**Deprecated/migration-flagged standards a working practitioner should recognize on sight and flag for replacement**: DES/3DES (Part 2), RC4 (Part 2), MD5/SHA-1 for any security-relevant purpose (Part 2), Dual_EC_DRBG (Part 4 — formally withdrawn), TLS 1.0/1.1 (deprecated by IETF in RFC 8996, 2021), export-grade cryptography artifacts of 1990s US crypto-export-control policy (still occasionally found lurking in old protocol negotiation code, and the direct historical cause of the 2015 FREAK and Logjam downgrade-attack families), and — on the horizon per Part 3's migration timelines — RSA and ECC themselves for anything with a multi-decade confidentiality requirement.
