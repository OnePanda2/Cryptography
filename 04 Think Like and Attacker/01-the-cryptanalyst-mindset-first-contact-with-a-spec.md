# 01 — The Cryptanalyst Mindset: First Contact With a Spec

*Part of a multi-file report — see `00-INDEX-executive-summary.md` for the map and how this report relates to its companions.*

## 1. The question that actually gets asked first

Reconstructing from how published cryptanalysis papers frame their own motivation, the first question an experienced cryptanalyst asks of a new specification is almost never "what attack can I try." It is: **"what does this design need to be true about its own internal randomness/independence/uniformity, and is there any reason to doubt it?"** Every primitive's security argument rests on some claim of this shape — that active nonlinear components behave independently round to round (companion ARX report `05` §1.7's Markov-assumption discussion), that a round's output looks uniformly random given a random input, that a keyed permutation's behavior under a chosen key is indistinguishable from its behavior under any other key. A cryptanalyst's actual first move is to identify, explicitly, *which* of these claims the design is resting its security argument on, because that claim — not the round function's specific operations — is the actual target.

This matters as a starting-point distinction because it inverts how the subject is usually taught. A student learns "here is differential cryptanalysis, here is linear cryptanalysis" as a menu and then asks "which one applies here?" An expert asks "what independence claim is this design making, and which known technique is best suited to falsifying *that specific claim*?" — the technique is chosen in service of a specific, already-identified target, not applied speculatively. TinyJambu's designers' own security proof (`04` of this report reconstructs this case in full) rested on an implicit independence claim about active AND gates across rounds; Saha et al.'s discovery process (per the paper's own stated contribution) was not "let's try differential cryptanalysis on TinyJambu" in the abstract — it was "the designers' MILP model assumes AND-gate independence; does that assumption actually hold?", and the answer (no) *was* the attack, once formalized.

## 2. What structural properties immediately attract attention

Reconstructing across the case studies in `04` and the attack-family literature in `05`, a short, genuinely reusable list of properties that reliably draw an experienced eye's attention on first read, each one a proxy for a specific kind of likely-false independence or uniformity claim:

- **Repeated structure across rounds with insufficiently-varied constants.** If two rounds look identical (same operations, same or trivially-related constants), the cryptanalyst's immediate question is whether the design's own diffusion argument secretly depends on rounds being *distinguishable* from each other in some subtle way the designer didn't state explicitly — this is exactly the property slide attacks and rotational/RX-cryptanalysis (companion ARX report `04` §2.4) exploit, and it's often visible on the very first read of a specification, before any formal modeling.
- **A nonlinear component whose "active" count is estimated via a simple counting argument.** Any time a specification states something like "an attack needs at least N active S-boxes/AND-gates/additions, therefore the attack probability is at most 2^(-cN)," the cryptanalyst's immediate, trained reflex is to ask whether that counting argument secretly assumes independence between the counted components — this is *exactly* the gap Saha et al. found in TinyJambu (`04`), and it's a general enough pattern that "check whether the active-component count assumes independence" is close to a standing checklist item for any new specification using this style of argument.
- **A design that reuses a countermeasure from an earlier, related design without restating why it works here specifically.** Rocca's key-dependent-initialization countermeasure, introduced to close one attack vector, later proved insufficient when a *different* cipher (HiAE) reused the same idea (`04`) — a cryptanalyst who's seen this pattern before treats "countermeasure X worked for design Y" as, at most, weak evidence that it works for design Z, and specifically goes looking for the ways Z's context differs from Y's.
- **A permutation being evaluated in a keyed mode when its original security case was made for an unkeyed (hash-function) use.** Keccak's zero-sum-distinguisher and cube-attack lineage (`04`) shows this pattern precisely: attacks against Keccak-MAC and Keyak (keyed uses) substantially outpaced attacks against plain Keccak-as-a-hash-function, because a keyed context gives an attacker leverage (the ability to make many queries under a fixed, unknown key) that an unkeyed hash function's security argument was never built to withstand — a specification that repurposes a permutation from one context to another without re-arguing security *for the new context specifically* is a standing invitation for exactly this class of attack.
- **A stated security *level* that isn't traceable to a stated security *proof*, or where the proof covers a narrower claim than the marketing prose implies.** Rocca's original security claims (`04`) were shown, by Hosoyamada et al., to not actually hold at the stated level — a direct instance of a design's prose overclaiming relative to what its formal argument, examined carefully, actually established.
- **Anything involving floating-point or non-integer arithmetic in a signing/sampling procedure.** Companion ARX report `03` §2.3's Falcon/FN-DSA Gaussian-sampling discussion is the standing current example — floating-point operations have execution-time and precision behavior that's much harder to argue is uniform/constant-time than integer ARX or SPN operations, and an experienced eye flags this immediately as a likely side-channel (not necessarily algebraic) weak point.

## 3. What makes a design "look suspicious" versus "look conservative"

A genuinely important, less-taught distinction: these warning signs are not a verdict — they're a **prioritization signal** for where to spend limited analysis time first, and an experienced cryptanalyst holds a clear, working distinction between "this looks suspicious" (a specific, checkable reason to suspect a specific weakness) and "this looks unconventional" (a design choice that's simply unfamiliar, which is a completely different, much weaker signal). A design with a genuinely novel state layout is *unfamiliar*, and unfamiliarity alone earns, at most, a slightly longer first read — it is not, by itself, evidence of anything (companion design-process report `01` §3's point that novelty is evaluated by "does newness earn its keep here," not "is this new," applies with equal force from the breaking side of the table). What earns genuine suspicion is specifically one of §2's list: an implicit independence claim, a reused countermeasure without fresh justification, a security level that outruns its own proof. Conflating "unfamiliar" with "suspicious" is a real, named failure mode (companion ARX report `08` §2.4's "overclaiming novelty" mistake has a mirror-image cryptanalyst-side version: *dismissing* an unfamiliar design as automatically weak, without doing the actual work to check, is just as much an error as a designer overclaiming an unfamiliar design's strength).

## 4. Where intuition actually comes from, and why it isn't shortcuttable

Reconstructing from the pattern visible across decades of published cryptanalysis (companion history report `06`–`08` trace this at the field level; this section states the individual-level version): the "intuition" experienced cryptanalysts describe developing "after reading hundreds of designs" is, concretely, the accumulation of a **library of paired (structural signature → technique that previously exploited it) associations**, built one real analysis at a time. A cryptanalyst who has personally worked through Keccak's zero-sum lineage has direct, first-hand calibration for "a distinguisher against the full round count doesn't automatically mean a break" that no amount of reading a *summary* of that lineage — including this report's own summary in `04` — fully replicates, because the calibration comes specifically from having sat with the gap between "I found a real structural anomaly" and "I have shown this anomaly matters," not from being told the gap exists. This is the report's most direct, if slightly uncomfortable, answer to "how do I get this intuition faster": there isn't a shortcut around doing the actual analytical work on real designs repeatedly; what this report *can* do is make the underlying pattern (§1's independence-claim-hunting, §2's specific warning-sign list) explicit enough that your own repeated practice builds the library faster and more deliberately than unstructured exposure would.

## 5. Patterns that repeatedly lead to broken systems, stated as a compact list

Synthesizing across every case study this report and its companions examine, the recurring *categories* of false claim that, historically, have most reliably produced a real break once found (not an exhaustive taxonomy — `05` covers the full attack-family catalog — but the specific *claims*, not techniques, that keep turning out false):

1. **"These operations are independent enough that we can multiply their individual probabilities."** (TinyJambu's AND-gate independence; the Markov-cipher assumption generally, companion ARX report `03` §1.5, `05` §1.7.)
2. **"This countermeasure, validated in context A, transfers to context B."** (Rocca → HiAE.)
3. **"A security argument made for use case A automatically extends to use case B."** (Keccak's hash-function security not automatically extending to its keyed-mode security.)
4. **"This statistical bias is too small to matter."** (RC4's early-byte biases, `04` — individually tiny, but real and, with enough traffic, exploitable.)
5. **"Our round count gives comfortable margin over the best attack we found."** — true at publication time, but silently false the moment a better attack technique is later invented against the *same* design without any change to the design itself (the entire ChaCha attack lineage traced in companion ARX report `04` §2.3 is this pattern playing out slowly, responsibly, and without ever actually reaching a break — the healthy version of this pattern, included here specifically to show it isn't always a story of failure).
