## 1. The decision an expert actually makes, and when

### 1.1 MILP versus SAT versus SMT versus CP — the real deciding factors

Restating companion ARX report `05` §2.4's comparison table with the decision logic made explicit: an expert's actual choice between these four tooling families, faced with a specific target, is driven by three practical factors, roughly in this order of weight — **(1) does the target's nonlinear operation have a native, efficient encoding in one framework but not another** (SMT's native bit-vector arithmetic handles addition more directly than raw SAT's CNF-decomposition requirement, per companion ARX report `05` §2.1; MILP's linear-inequality encoding of addition, per `05` §1.4, is well-trodden and benefits from mature commercial solvers); **(2) is the goal finding the single optimal trail (MILP's traditional strength, given a clean objective-function formulation) or proving infeasibility/existence (SAT's traditional strength, given a clean satisfiability question)**; and **(3) which tool has the most existing, purpose-built cryptanalytic tooling already wrapping it for this specific target family** — CryptoSMT and CLAASP (companion ARX report `05` §1.6) exist specifically to remove the raw-encoding burden from this decision, and an expert's practical first move, more often than choosing a raw solver, is checking whether an existing framework already has support for the target's operation set before building anything from scratch.

### 1.2 When hand-reasoning is still faster than any tool

Directly restating `02` Stages 3–4's funnel logic from the tooling-decision side: a symmetry check, a fixed-point count, or a diffusion-heatmap computation is genuinely faster to do by hand or via a five-line script than to formally encode into any of §1.1's frameworks — and an expert who reaches for full automated tooling before exhausting the cheap, hand-reasoned checks is, per this report's `02` and companion ARX report `05` §1.7's common-mistakes discussion, working less efficiently than the field's actual best practice, not more rigorously.

### 1.3 When the investment in a full formal model is justified

Per `02` Stage 5–6's escalation logic: once a cheap check has surfaced a specific, non-obvious lead (a differential trail that looks uncomfortably strong through several hand-traced rounds; a symmetry that survives initial inspection but whose full consequences are hard to trace by hand past a few rounds), building a correct MILP or SAT model of the *full* round function — genuinely expensive in researcher time, per companion ARX report `05` §1.4's discussion of exactly how much careful bit-level encoding work modeling addition correctly requires — becomes worth it specifically because hand-tracing has hit its own complexity ceiling, not because "more rigor is always better."

### 1.4 When differential-neural / ML-assisted techniques specifically get reached for

Two genuinely distinct triggers, worth keeping separate: **(a) the target closely resembles an already-well-studied benchmark family** (Speck/Simon/Simeck specifically) where substantial trained-model infrastructure, architecture choices, and comparison baselines already exist (companion ARX report `04` §2.10's DbitNet and related lineage) — here the marginal cost of applying the technique is low because the infrastructure investment has already been amortized across the field's prior work; **(b) the target's stakes are high enough to justify building new infrastructure from scratch even absent an existing benchmark match** — the July 2026 HAWK event (companion ARX report `04` §2.10, `09` §3.3; companion history report `05`) is the clean example of trigger (b): HAWK doesn't resemble Speck/Simon structurally at all (it's a lattice-based signature scheme, not an ARX block cipher), meaning the sustained, substantially autonomous research effort Anthropic describes had to be justified by the target's live NIST-standardization stakes, not by cheap infrastructure reuse.

## 2. The Tool Landscape — Strengths, Weaknesses, Typical Use

| Tool | Strength | Weakness | Typical trigger for reaching for it |
|---|---|---|---|
| **Gurobi / CPLEX (MILP)** | Industrial-grade, provably-optimal trail search at real cipher scale | Requires correct, often labor-intensive bit-level encoding of the target's nonlinear operation | Once a target has survived cheap checks and a specific round-function/rotation-schedule needs an optimal (not just any) trail bound |
| **CryptoMiniSat and other cryptanalysis-tuned SAT solvers** | Fast on cryptographically-structured CNF instances specifically | CNF encoding of arithmetic (especially addition) is less natural than MILP's linear-inequality form | Feasibility/existence questions (does *any* trail below weight W exist), and RX-differential search specifically (companion ARX report `04` §2.4's CNF-based framework) |
| **SMT solvers (via CryptoSMT and similar)** | Native bit-vector arithmetic — addition doesn't need manual decomposition | Generally less battle-tested for this exact workload than dedicated MILP/SAT tooling | Rapid prototyping of a new target's model before committing to a heavier MILP encoding |
| **CP-SAT (Google OR-Tools)** | Flexible constraint language, strong hybrid search | Newer to this specific research community than MILP/SAT | Problems naturally expressed as CNF-like clauses but benefiting from CP's more flexible constraint language (companion ARX report `05` §2.2) |
| **CLAASP** | Define a new primitive once, get MILP/SAT models auto-generated across multiple analysis types | Still requires the researcher to correctly specify the primitive's structure | Exactly your stated goal — evaluating a genuinely new ARX design, not just re-analyzing an existing well-studied one |
| **The Window Heuristic-class tooling** | State-of-the-art partial-linearization trade-off for modular addition specifically | Newest, least battle-tested across the widest range of targets | Pushing a differential-trail search further than older addition-modeling approaches can reach, on a target where every bit of extra search depth matters |
| **Differential-neural training pipelines (Gohr-lineage, DbitNet)** | Can match or exceed hand-derived distinguishers empirically, sometimes finding structure classical methods miss | Requires ML infrastructure and training-data generation; interpretability of *why* it works remains actively contested (companion ARX report `04` §2.10) | Speck/Simon/Simeck-family targets, or high-stakes targets justifying fresh infrastructure investment |
| **Symbolic execution tools (general-purpose, not cryptanalysis-specific)** | Systematic exploration of an implementation's actual code paths, catching implementation-layer bugs a pure algorithm-level model would miss | Not purpose-built for cryptanalytic trail search; better suited to catching Heartbleed-class memory-safety and logic bugs (companion general-cryptography report `04` §1.5's implementation-vs-algorithm distinction) | Implementation review specifically (`02` Stage 7), not algorithm-level cryptanalysis |
| **Formal verification / proof assistants (Coq, Lean, Isabelle, HACL\*'s F\* pipeline)** | Machine-checked correctness and, increasingly, constant-time guarantees on actual compiled code | Substantial researcher-time investment; still the exception, not the baseline, for a typical new-design evaluation (companion design-process report `07` §4's table) | High-assurance implementation verification, once a design is mature enough to be worth this investment |

## 3. Research Frontier

Restating and extending companion ARX report `09` §3.4's projection with this report's discovery-process framing added: the genuine open frontier isn't primarily "better solvers" (MILP/SAT tooling is comparatively mature, per companion ARX report `05` §1.6–1.7) but **better automated *triage*** — tooling that helps a cryptanalyst decide, cheaply and early, *which* of `03`'s warning-sign catalog is actually worth escalating to expensive formal modeling for a specific new design, rather than tooling that makes the expensive formal modeling step itself faster. This is a genuinely different research problem than the one most current automated-cryptanalysis papers address (which overwhelmingly improve the expensive-modeling stage, per companion ARX report `05`'s bibliography), and, per this report's own `01` §4's point about intuition being built through repeated practice rather than shortcut, may be intrinsically harder to fully automate — triage, as this report has tried to make explicit throughout, is closer to pattern-matched judgment than to a formalizable search problem, and whether that judgment can itself be usefully automated (as distinct from the specific formal-modeling steps downstream of it) is, honestly, an open question this report declines to predict the answer to.
