## 1. State Design — Sizing the Canvas

### 1.1 State size as a negotiation, not a single variable

State size (256, 384, 512, 1024 bits) is never chosen in isolation — it's the resolved output of a negotiation between three pulls that genuinely fight each other: **security headroom** (a wider state gives more generic-attack margin — more room between the claimed security level and the birthday-bound-style generic attacks that scale with state size, per companion ARX report `02` §1.4), **performance cost** (more state means more per-round computation and, critically, more live register/SIMD-lane occupancy per round, directly threatening the register-pressure concerns of `02`'s implementation discussion), and **target-platform fit** (a state that doesn't map cleanly onto the target platform's natural register/SIMD width leaves performance on the table regardless of the round function's quality). The Sparkle family's three named variants (Sparkle256/384/512) are the clearest visible artifact of a design team explicitly refusing to resolve this negotiation once — they shipped three points on the tradeoff curve, each targeting a different combination of security level and footprint constraint, rather than pretending one size fits every deployment context. **The reconstructable lesson**: if you find yourself defending a single state size as "the" right answer rather than being able to articulate what a smaller or larger variant would trade away, you likely haven't actually done this negotiation — you've picked a number that felt right.

### 1.2 Word size as a hardware-register decision, disguised as a math decision

Word size (32-bit, 64-bit) reads, in a specification, like a purely mathematical choice (how many bits does the adder operate on), but every reconstructable design decision behind it is actually a **hardware-register-width** decision first. ChaCha and Salsa20's 32-bit words are not chosen because 32 bits has some special cryptographic virtue — they're chosen because 32-bit is the smallest register width that's *native* on essentially every general-purpose CPU built since the 1980s, meaning a 32-bit-word design never needs to synthesize wider arithmetic from narrower registers on any realistic target platform (companion ARX report `01` §2.8). BLAKE2b and SipHash's 64-bit words reflect exactly the same logic one register-generation later, once 64-bit became the dominant native width. **The decision procedure, reconstructed**: identify the *narrowest* native register width across your full target-platform list (§4 of `01`), and default to that as your word size unless a specific, stated reason (need for a longer carry chain to accumulate more addition-based nonlinearity per operation, per companion ARX report `01` §2.2, at the cost of needing more rounds' worth of automated verification to confirm the accumulated margin is real) argues for going wider.

### 1.3 Lane count, register layout, and the SIMD-alignment decision that shapes everything downstream

The number of parallel "lanes" (independent words a round function operates on simultaneously) is chosen, per ChaCha's reconstructable design history, specifically to **divide evenly into common SIMD register widths** — ChaCha's 16-word state maps exactly onto four 128-bit SIMD registers (four 32-bit words each), which is not a coincidence but a design decision made early enough to shape the state layout itself, not discovered as a happy accident during later implementation work. **This is the single most consequential "hidden" decision this report can surface**: a designer who picks state size and lane count purely from security-margin reasoning, without checking lane-count-against-SIMD-width divisibility, will produce a specification that a later implementer has to work around — misaligned lane boundaries relative to SIMD register width force either wasted lanes (padding) or awkward, hard-to-vectorize access patterns, and this cost is *baked into the specification itself*, unfixable by implementation cleverness alone. Every case study in `05` that achieved genuinely excellent real-world software throughput (ChaCha, BLAKE3) made this alignment decision explicitly and early; designs that didn't tend to underperform their raw operation-count would predict, for reasons only visible once you look at register/SIMD alignment specifically.

### 1.4 Cache-friendliness and future scalability

**Cache-friendliness** for an ARX/permutation design is largely a non-issue in the side-channel sense (companion history report `01`, `07` §1.1 — no secret-dependent memory access exists to leak), but remains a genuine *aggregate footprint* question: does the full state plus working code fit comfortably in L1 cache without displacing the surrounding application's own cache-resident data — a real, if secondary, performance consideration distinct from the side-channel question, worth stating explicitly as a design-time check rather than an afterthought. **Future scalability** — can the same design family be extended to a larger or smaller state without a full redesign — is exactly what Sparkle's three named variants and Speck/Simon's many block/key-size combinations both demonstrate as a deliberate design-time decision: build the round function's *structure* to be parametrizable across state sizes from the outset, rather than hand-crafting a single fixed size and hoping it generalizes later.

## 2. Round Function Invention — How the Actual Nonlinear/Linear Machinery Gets Built

### 2.1 The honest process: constrained brainstorming and elimination, not sudden insight

Reconstructing from every case study's available design-rationale documentation, round-function invention looks far less like a single flash of insight and far more like **generating several structurally-different candidate round functions that each satisfy the architecture choice from `01`, then eliminating candidates against the requirements from `01` §4 one at a time**, in a specific, reconstructable order:

1. **First elimination pass — does the candidate deliver the architecture's core promise at all?** An ARX candidate that secretly relies on a table lookup somewhere isn't actually ARX; a candidate proposed for a hardware-constrained target that requires wide multiplication (expensive in gates) fails immediately regardless of its other merits. This pass is fast and mostly disqualifies candidates on structural grounds alone, before any cryptanalysis is needed.
2. **Second elimination pass — rough diffusion-speed estimation.** Before any automated trail search, designers estimate (often by hand, or via a quick script) how many rounds a candidate needs to reach full, SAC-compliant state dependency (companion ARX report `03` §2.1) — a cheap, fast proxy that eliminates candidates needing an obviously excessive round count to reach adequate diffusion, without yet investing in expensive automated-search evaluation of every survivor.
3. **Third elimination pass — rough performance estimation.** Instruction-count and register-pressure estimates (companion ARX report `07` §3.3) for the surviving candidates, checked against the performance goal stated in `01` §4 — a candidate that clears diffusion-speed screening but needs, say, twice the instructions-per-byte of the stated comparison-point target gets eliminated here, before expensive full cryptanalytic evaluation.
4. **Fourth elimination pass — genuine automated-search cryptanalytic evaluation.** Only the survivors of passes 1–3 — typically a small handful of candidates, not the dozens that may have existed at the brainstorming stage — receive full MILP/SAT trail-search treatment (companion ARX report `05`). This ordering (cheap structural/diffusion/performance screens first, expensive cryptanalytic modeling last) is not arbitrary; it's the only economically sensible order, since building a full MILP model for a round function is genuinely expensive in researcher time, and no serious designer builds one for a candidate that a five-minute diffusion estimate would have already eliminated.

**Why this reconstructed process matters more than any specific round function**: it explains why published round functions look, in retrospect, almost inevitable — ChaCha's quarter-round reads as an obvious, clean design once you see it, but that cleanness is the *output* of this elimination process having already discarded every messier, less-obviously-correct candidate, not evidence that the clean version was the first or only thing tried.

### 2.2 Mixing layers, diffusion layers, and the confusion/diffusion division of labor

Every round function this report examines cleanly separates, structurally if not always in prose, which operations deliver **confusion** (nonlinearity — addition's carry chain, for ARX; the S-box, for SPN) and which deliver **diffusion** (rotation and cross-lane XOR, for ARX; the linear mixing/permutation layer, for SPN) — companion history report `06`'s confusion/diffusion thread traces this division all the way back to Shannon. **The design-process implication**: a round function candidate that tries to get *both* confusion and diffusion from the same operation (rather than cleanly assigning each to a distinct step) is measurably harder to formally analyze, because the wide-trail/long-trail-strategy proof techniques (companion ARX report `03` §1.4) both depend on being able to reason about the nonlinear and linear components *separately* before combining their bounds — a round function that entangles the two doesn't just look messier, it genuinely resists the field's best available proof machinery, which is a real, technical reason (not merely an aesthetic one) that clean confusion/diffusion separation keeps winning out as candidates get eliminated in §2.1's fourth pass.

### 2.3 Carry propagation, nonlinearity budgeting, and rotation schedules as a joint decision

For an ARX round function specifically, the amount of nonlinearity delivered per round is a direct function of how many additions occur and how far each addition's carry chain is allowed to propagate before being "reset" by an intervening rotation (companion ARX report `01` §2.2, §2.6) — meaning **rotation-schedule choice and nonlinearity budgeting are not separable decisions**, even though they're often presented as sequential steps in a specification's prose. A round function with too few additions, or additions whose carry chains get reset too early by aggressively-chosen rotation amounts, under-delivers on confusion regardless of how many rounds it runs; a round function with additions whose carry chains are allowed to run too long before any rotation intervenes over-concentrates nonlinearity in high-order bits, leaving low-order bits comparatively under-mixed (companion ARX report `01` §2.2's bit-position-non-uniformity point) — the actual design skill here is **balancing** these against each other, and Part `03` of this report picks up the rotation-constant-specific half of that balance in full process detail.

### 2.4 Constant injection and key injection — where and why

Round-constant injection exists, mechanistically, for exactly one reason worth stating precisely: **to break symmetries a pure add-rotate-XOR structure would otherwise retain** — a round function with identical structure and no varying constants across rounds is, generically, vulnerable to slide, rotational, and RX-cryptanalytic attacks that exploit exactly that repeated structure (companion ARX report `04` §2.4, §1.4). The design decision this report can reconstruct explicitly: constants should be chosen specifically to *not* be rotation-invariant (defeating rotational/RX-symmetry) and specifically to differ round-to-round (defeating slide-style attacks), and — per the "nothing up my sleeve" provenance-transparency norm this conversation's history report traces to the post-2013 Snowden-driven trust environment (companion history report `03`, `07` §1.5) — should be generated via a fully reproducible, auditable procedure (a fixed mathematical sequence like digits of a well-known constant, or a simple counter) rather than chosen by hand, so that no one can later credibly suspect the constants were engineered for some hidden weakness. **Key injection point placement** is a related but distinct decision — where in the round structure key material enters affects both performance (key-dependent precomputation opportunities) and security (related-key attack resistance, companion ARX report `04` §2.7), and the reconstructable pattern across successful designs is to inject key material at a small number of clearly-defined points (often just the initial state and, for longer-running constructions, periodically thereafter) rather than scattering it unevenly, specifically because a simple, uniform key schedule is easier to analyze for related-key weaknesses than a complex one, and — per §2.1's elimination-pass logic — added key-schedule complexity needs to buy proportionate security benefit to survive the performance-cost elimination pass.

## 3. Topology Design — Inventing State Layouts

### 3.1 Columns, rows, and diagonals as the base vocabulary

The base topological vocabulary — apply a round function to columns of a state grid, then to rows or diagonals in the next round — exists because a single grouping alone (columns only, say) can never mix data *between* groups, no matter how many rounds run (companion ARX report `02` §1.2's explicit statement of this for Salsa20/ChaCha). **The reconstructable design principle**: topology design is fundamentally about choosing a *sequence of groupings* such that every pair of state words ends up in the same group at some point within a small number of rounds — this is a graph-connectivity problem in disguise (§3.3 below), and the column/row/diagonal vocabulary is simply the most easily hand-reasoned-about family of groupings that solves it for small, grid-shaped states.

### 3.2 Cross-lane mixing, butterfly networks, and shuffle layers

For designs with more lanes than a simple 4×4 grid comfortably supports, or for designs prioritizing especially fast full-state diffusion in very few rounds, more elaborate topologies borrow directly from classical computer-science interconnection-network theory: **butterfly networks** (the same log(n)-depth, full-connectivity-in-log-time structure used in FFT computation and sorting networks) offer a principled way to guarantee full pairwise connectivity in a minimal, *provably*-bounded number of rounds, at the cost of a less regular, harder-to-hand-reason-about wiring pattern than simple column/row/diagonal grouping. **Shuffle layers** (permuting lane positions between rounds via a fixed, often bit-reversal-derived permutation) serve an analogous purpose with a different, often more hardware-friendly wiring cost profile. **Why these appear less often in the case studies this report examines than the simpler column/diagonal vocabulary**: per §2.1's elimination logic, a topology that's harder to hand-reason-about is harder to build early diffusion-speed intuition for during the cheap screening passes, and harder for reviewers to independently verify later (`04`) — meaning butterfly/shuffle-style topologies tend to appear specifically in designs targeting very wide states or very aggressive minimal-round-count goals, where the extra analytical cost is justified by a correspondingly large payoff, rather than as a general-purpose default.

### 3.3 State graphs, dependency graphs, and connectivity analysis as an actual design tool

The formal tool underlying all of the above, made explicit rather than left as hand-wavy intuition: model the state as a graph where nodes are words (or bits, for finer-grained analysis) and edges represent "this operation makes node A's value depend on node B's value within one round" — then **topology design is literally the graph-design problem of choosing edges (which words interact in which operations) such that the graph's diameter (longest shortest-path between any two nodes) is minimized for a given edge-count/complexity budget**, since diameter directly bounds the minimum number of rounds needed for full-state dependency. This is not a metaphor; it's the actual mathematical object several published automated-topology-search efforts (§4 below) optimize over directly, and even designers who never formally build the graph are, per the reconstructable pattern across every case study, implicitly reasoning about exactly this object when they sketch candidate column/diagonal/butterfly groupings on paper and ask "how many rounds until everything touches everything."

### 3.4 Automatic topology search — where the field currently stands

As of 2026, per this conversation's companion ARX-specific report (`09` §3.4), **fully automated search over the topology space itself** — not just over rotation constants given a fixed topology (companion ARX report `04` §1.2), but over the *grouping/wiring structure* itself — remains a comparatively underexplored, genuinely open research direction rather than an established, routinely-used design tool. Most current automated-search tooling (CLAASP, the Window Heuristic) is built to *evaluate* a human-proposed topology's security properties efficiently, not to *generate* candidate topologies from scratch — meaning topology invention, as of this report's writing, remains substantially a human, hand-reasoned activity guided by the column/row/diagonal/butterfly vocabulary above, evaluated automatically only once a specific candidate topology has already been chosen. This is a genuine, current gap between "we can automatically check if a topology is good" and "we can automatically search for a good topology," worth naming explicitly for exactly the audience this report addresses (someone who eventually wants to design their own permutation) — it means topology invention is currently one of the few remaining steps in this entire process where hand-reasoning still carries most of the weight, not automated tooling.
