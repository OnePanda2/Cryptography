# 01 — Philosophy of Evaluation and the Epistemic Hierarchy

*Part of a multi-file report — see `00-INDEX-executive-summary.md` for the map. This file is new conceptual material, not a restatement of any companion report.*

---

## 1. Why evaluation exists at all

Evaluation exists because a cryptographic primitive's designer is structurally the worst-positioned person to certify their own design — not from any lack of skill, but because they know exactly what they built the design to resist, and a design's actual failure mode is, overwhelmingly, something the designer didn't think to check (companion cryptanalyst-mindset report `01` §1's entire framing — a designer's security argument rests on specific claims, and it's precisely the claims *they didn't think to question* that turn out false). Evaluation is the field's answer to this structural blind spot: a process, external to the design act itself, whose entire purpose is manufacturing exactly the scrutiny a designer cannot manufacture for themselves. This is why every companion report in this conversation converges on the same conclusion from different angles — companion design-process report `03` §3.4 defines design maturity as "having done everything internally checkable, with the honest next step being external scrutiny"; companion cryptanalyst-mindset report `07` §1.3 defines adequate vetting as scrutiny from genuinely different specializations, not merely time elapsed. Evaluation is not a formality layered on top of design; it is the mechanism by which the field's actual trust gets manufactured, because internal confidence, however sincerely held, is not evidence.

## 2. Why apparently good designs fail, and apparently weak designs survive

**Apparently good designs fail** for a specific, recurring reason this report's companions have already documented with real cases: the design's own evaluation was thorough along the dimensions its designers thought to check, and silent along a dimension they didn't — TinyJambu's independence-assumption gap (companion cryptanalyst-mindset report `04`) is the cleanest example in this entire conversation's material, precisely because the designers *did* run a serious, standard evaluation methodology (MILP-based active-gate counting); the failure wasn't a lack of rigor, it was an unexamined assumption baked invisibly into an otherwise rigorous method. **Apparently weak designs survive** for the mirror reason: a design that looks unconventional or inelegant (companion design-process report `01` §3's "unfamiliar versus suspicious" distinction) can be perfectly sound if its actual claims — however plainly or awkwardly stated — happen to be true, and aesthetic judgment about a design's elegance is, per every companion report in this conversation, explicitly *not* a reliable proxy for its actual security, in either direction.

## 3. Measurement, evidence, proof, confidence, security — five distinct things

This is the report's central conceptual tool, worth stating with full precision because the rest of this report tests every subsequent evaluation practice against it.

**Measurement** is the output of a well-defined, mechanical procedure applied to a specific artifact: a SAC dependency-matrix entry, a PractRand p-value, a cycles-per-byte figure, a differential trail's MILP-computed weight. A measurement is, in isolation, neither good nor bad news — it's a number, and its meaning depends entirely on what's done with it next.

**Evidence** is a measurement (or set of measurements) interpreted against a specific claim, with an explicit account of how strongly it bears on that claim and under what conditions it would have looked different if the claim were false. "This trail has MILP-weight 128" is a measurement; "no MILP-found trail below weight 128 exists across the full search space we defined, which we've verified would have found the design's own claimed weaker bound if it existed" is evidence — the difference is the explicit falsifiability check (companion design-process report `01` §2's falsifiable-hypothesis discipline, restated here as an evaluation-side requirement, not just a design-side one).

**Proof**, in this field's technical sense, is a mathematical demonstration that one statement implies another — almost always conditional (companion general-cryptography report `02` §6's point that essentially nothing in modern cryptography is unconditionally proven secure; every proof reduces security to some hardness assumption). A proof is the strongest form of evidence this report catalogs, and it is *still not the same thing as security*, because it inherits every uncertainty in the assumption it's conditioned on, and because — per companion ARX report `05` §3's random-oracle-model discussion and companion general-cryptography report `01` §2.6's Canetti-Goldreich-Halevi result — even a correctly-executed proof can rest on an idealization (the ROM, the ideal permutation model) that is itself only an approximation of how the real, deployed artifact will behave.

**Confidence** is the epistemic state a design team, a reviewer, or a standards body actually ends up in after weighing all available measurement, evidence, and proof together — and, critically, confidence is **calibrated and revisable**, not binary. A well-functioning field holds different confidence levels about AES (multi-decade, extremely broad scrutiny, essentially no reasonable doubt remaining) and about a newly-published PQC candidate (recently proposed, scrutiny still accumulating, appropriately less confidence) — treating these two cases with the same binary "proven secure / not proven secure" label would erase a distinction that matters enormously in practice, and is precisely the distinction companion history report `07` §1.2's SIKE case study shows the field learning to take seriously the hard way (round-survival is not proof, and confidence should scale with the *breadth and duration* of scrutiny received, not merely its absence of failure).

**Security** is the actual, real-world property the previous four concepts are all trying to approximate — and it is, in the fullest sense, unknowable with certainty for any primitive currently in use, because knowing a design is secure with certainty would require ruling out every possible future attack technique, including ones not yet invented. This is not cynicism; it's the honest, stated position every companion report in this conversation has taken when the topic has come up (companion ARX report `00`'s "never hide uncertainty" methodology commitment, restated here as this report's own governing principle), and internalizing it is what separates a mature evaluator from one who treats "passed every test we ran" as equivalent to "is secure."

## 4. Where this hierarchy gets violated in practice, stated as a preview

Every subsequent file in this report is, in a real sense, a catalog of specific places this five-level hierarchy collapses in actual practice — a measurement reported as if it were evidence (an unqualified PractRand pass, `04`); evidence reported as if it were proof (a found-trail-free MILP search treated as certainty rather than a bound conditional on the Markov assumption, `03`, `05`); proof treated as if it settled confidence permanently rather than needing to accumulate alongside real-world scrutiny over time (`06`'s evaluation-failures catalog). Keeping the five levels genuinely distinct, at every stage of an evaluation pipeline, is this report's single organizing discipline, and `08`'s capstone pipeline is built explicitly to enforce it stage by stage rather than assume it happens automatically.

Part `02` (`02-the-evaluation-pipeline-and-controls.md`) now reconstructs the full evaluator's workflow this philosophy is meant to operate inside of, with explicit attention to positive and negative controls as the specific mechanism that keeps a measurement from silently becoming mistaken for evidence.
