## 1. Sampling and Noise — the Foundational Fact Every Downstream Section Depends On

Nearly every measurement this report's companions describe — a SAC dependency-matrix entry, a PractRand/BigCrush p-value, a cycles-per-byte figure — is an **estimate computed from a finite sample**, not an exact, noise-free quantity. This sounds obvious stated directly, but its consequences are routinely under-handled in practice: an estimate computed from a finite sample has a **sampling distribution**, and any single computed number is one draw from that distribution, not the truth itself. Every technique in this file exists to answer one question, asked in a specific, cryptographically-relevant context each time: *given that this number is a noisy estimate, how much can I actually conclude from it?*

## 2. Confidence Intervals — Applied to a SAC/BIC Entry Concretely

A SAC dependency-matrix entry (companion ARX report `03` §2.1) is, mathematically, an estimate of a Bernoulli probability: over N random single-bit-flip trials, what fraction of trials flip a given output bit? The **standard error** of this estimate is approximately 0.5/√N when the true probability is near the ideal 0.5 value — meaning:

| Sample size N | Approximate 95% confidence interval half-width around 0.5 |
|---|---|
| 2^10 (1,024) | ±0.031 |
| 2^16 (65,536) | ±0.0038 |
| 2^20 (1,048,576) | ±0.00096 |
| 2^24 (16,777,216) | ±0.00024 |

**The concrete, actionable point this table makes**: a design tested with only 2^10 trials cannot distinguish a genuinely SAC-compliant round function from one with a real, cryptanalytically-relevant bias as large as 0.02–0.03 — the noise floor at that sample size is larger than a bias that could matter. A published diffusion evaluation that reports "SAC deviation under 0.01, therefore compliant" without stating the sample size the deviation was measured at is not yet a complete claim — the same 0.01 figure is strong evidence at N=2^24 and essentially uninformative at N=2^10, and the difference is invisible unless the sample size is reported alongside it. **The general practice this table argues for**: report confidence intervals, not point estimates, for every sampled diffusion/randomness measurement, and choose sample size deliberately (via the power-analysis logic in §5) rather than by convention or convenience.

## 3. Statistical Significance Versus Effect Size — Why They Answer Different Questions

**Statistical significance** answers "is this deviation from the ideal larger than sampling noise would plausibly produce." **Effect size** answers "how large is the deviation, in units that matter for the actual question" — and these are genuinely different questions whose answers can point in opposite directions. At an enormous sample size (say, 2^30 trials), a true bias of 0.0001 — almost certainly cryptanalytically irrelevant, since it would require an attacker to observe an astronomically large number of samples to exploit — will register as "statistically significant" with high confidence, because the sampling noise at that scale is even smaller than the bias itself. Conversely, a real, security-relevant bias of 0.02 tested at only 2^10 trials may not register as statistically distinguishable from noise at all, per §2's table. **The correction this report argues for, specific to cryptographic evaluation**: don't ask "is this deviation statistically significant" in isolation — ask "is this deviation large enough that, translated through the standard differential/linear complexity formulas (roughly, an attack complexity on the order of 1/ε² or 1/ε for a bias of size ε, depending on the attack family, companion ARX report `04`), it would meaningfully lower the design's claimed security level." A deviation should be evaluated against this security-relevant effect-size threshold *first*, with statistical-significance testing used only to establish whether the measured deviation is even real (versus noise) at the sample size actually used — significance without a security-relevant effect size is not actionable; a security-relevant effect size without statistical significance means you haven't sampled enough to know yet, not that there's nothing there.

## 4. Multiple Comparisons and False Discovery — the Diffusion-Matrix-Specific Version

A full SAC/BIC dependency matrix for an n-bit-input, m-bit-output function contains n×m individual entries (or more, for BIC's pairwise-output-bit version) — each one a separate statistical test. **This is a textbook multiple-comparisons scenario**, and it has a specific, well-understood consequence: if you set a per-entry significance threshold of, say, p<0.05 for "this entry deviates significantly from the ideal," and you have, say, 1,024 entries in your matrix, you should *expect* roughly 51 entries to cross that threshold **purely by chance**, even for a perfectly SAC-compliant design — not because anything is wrong, but because running a thousand independent tests at a 5%-false-positive-rate threshold produces, on average, fifty false positives. **The specific, actionable consequence for diffusion evaluation**: a single flagged cell in a large dependency matrix is, on its own, close to meaningless — what matters is whether the *number* of flagged cells substantially exceeds what the multiple-comparisons-corrected false-discovery rate would predict, or whether flagged cells **cluster** in a structurally meaningful way (the same output bit, or the same input-bit region, repeatedly flagged across independent trials) rather than being scattered uniformly across the matrix the way pure chance would produce. Standard corrections — **Bonferroni** (divide your significance threshold by the number of tests, a conservative but simple fix) or the **Benjamini-Hochberg false-discovery-rate procedure** (a less conservative, more statistically efficient correction that controls the *expected proportion* of false positives among flagged results rather than the probability of *any* false positive) — are standard, well-established statistical tools directly applicable here, and their absence from a diffusion-evaluation report is a real, checkable gap.

## 5. Power Analysis — Deciding Sample Size *Before* Running the Test

**Statistical power** is the probability that a test correctly detects a real effect of a specified minimum size, given the sample size and significance threshold chosen. **The discipline this report argues for, stated as a concrete workflow step missing from most published cryptographic evaluation practice**: before running a diffusion or randomness test, decide what minimum bias size would actually matter (per §3's security-relevant-effect-size framing), then compute — using the standard-error formula in §2, inverted — the sample size needed to detect a bias of that size with adequate power (conventionally 80% or higher, meaning the test would correctly flag a real effect of the stated size at least 80% of the time it's actually present). Running a test *without* this calculation risks two symmetric failure modes: **under-powering** (too small a sample to detect a real, relevant bias, producing false confidence — the specific mechanism behind `01` §4's "measurement mistaken for evidence" category error), and **wasteful over-powering** (a far larger sample than needed to detect the relevant effect size, burning compute budget that could have gone toward a different stage of the pipeline, per companion cryptanalyst-mindset report `02`'s cost-escalating-funnel logic applied here to statistical sample-size budgeting specifically).

## 6. Applying This to Randomness Test Suites Specifically

PractRand and TestU01/BigCrush (companion ARX report `06` §2.1) are themselves already, internally, multiple-comparisons-aware to a real degree — BigCrush runs on the order of dozens of distinct sub-tests, each potentially producing multiple p-values across different parameterizations, and the field's established convention (reflected in both suites' own documentation and standard practice around them) is specifically **not** to treat a single marginal p-value (say, in the 0.01–0.05 range) as a definitive failure — the accepted practice is to **re-run the specific flagged sub-test with fresh, independently-seeded data** and check whether the marginal result replicates; a result that vanishes on a fresh seed was very likely a false positive of exactly the kind §4 describes, while a result that persists across independent re-seeding is much stronger evidence of a genuine anomaly. **This re-run-on-flag convention is, in effect, a built-in replication discipline (§8 below) specifically designed to manage the multiple-comparisons problem these large test batteries inherently create** — worth stating explicitly because it's easy to use these suites mechanically (run the battery, check for an overall pass/fail) without understanding *why* the convention around interpreting marginal results exists, and a user who doesn't understand the convention is liable to either over-react to an isolated marginal p-value or, worse, under-react to a genuinely replicating one by not knowing the re-run step is expected practice at all.

## 7. Sensitivity Analysis and Robustness Testing

A conclusion is **robust** if it doesn't change under reasonable variation in the nuisance parameters of the test that produced it — which random seed generated the test inputs, exactly which sample size within a reasonable range was used, which specific sub-battery of a larger test suite was run first. **The concrete check this section argues for**: rerun any load-bearing evaluation conclusion (a diffusion result, a randomness-test verdict, a benchmark comparison) with a different seed and, ideally, a meaningfully different sample size, and confirm the conclusion doesn't flip. A conclusion that's sensitive to exactly which seed happened to be used is fragile in a way that should itself be reported — not hidden by simply not mentioning that a different seed was ever tried — because a fragile conclusion, even if the specific number reported is technically accurate for the one seed used, is a weaker piece of evidence than a robust one, and `01` §3's evidence-versus-measurement distinction depends on being honest about exactly this kind of fragility.

## 8. Replication as a Statistical, Not Just Procedural, Discipline

Restating companion ARX report `08` §1.3 and companion cryptanalyst-mindset report `07` §1.2's replication points with the statistical framing this file develops layered on: replication isn't just "did someone else run the same code" — it's specifically **an independent draw from the same underlying sampling distribution**, and its statistical value comes precisely from being independent (a different seed, ideally a different implementation, ideally a different researcher) rather than a mechanical re-execution of the identical procedure with the identical inputs, which would only catch a narrower class of errors (a non-deterministic bug, say) than genuine independent replication catches (a systematic error in the *original* methodology itself, which a mechanical re-run of the same code would faithfully reproduce rather than reveal).

## 9. Measurement Uncertainty in Non-Statistical Contexts — Where This Framework Doesn't Apply, Stated Honestly

Not every quantity this report's companions discuss is a sampled estimate — an MILP-solver-computed optimal trail weight, for a *specific*, *fully-specified* round function and round count, is an **exact** computation (given correct modeling), not a statistical estimate, and §1–8's machinery doesn't apply to it directly in the way it applies to a SAC entry or a PractRand p-value. **Where the uncertainty in an MILP/SAT result actually lives, instead**: not in sampling noise, but in the **Markov-cipher assumption** (companion ARX report `03` §1.5, `05` §1.7) — the assumption that per-round probabilities can be multiplied independently across rounds to estimate the full trail's probability. This is a *modeling* uncertainty, not a *sampling* uncertainty, and it calls for a different kind of check (companion ARX report `05` §1.7's explicit recommendation to sanity-check the Markov assumption experimentally for the specific design in question) rather than a confidence interval — a genuinely important distinction worth stating precisely, since conflating "this number has sampling uncertainty" with "this number has modeling uncertainty" leads to applying the wrong corrective technique (running more MILP searches doesn't shrink Markov-assumption uncertainty the way running more trials shrinks sampling uncertainty, and treating the two as interchangeable is its own, subtler category error).

## 10. A Compact Statistical Checklist

- [ ] Every sampled measurement (diffusion metric, randomness-test statistic) reported with its sample size and, ideally, an explicit confidence interval.
- [ ] Sample size chosen via an explicit power-analysis argument against a stated, security-relevant minimum effect size — not by convention or convenience alone.
- [ ] Multiple-comparisons correction (Bonferroni or Benjamini-Hochberg) applied, or at minimum explicitly discussed, for any test involving many simultaneous comparisons (a full dependency matrix, a large test-suite battery).
- [ ] Statistical significance and security-relevant effect size reported and interpreted as genuinely distinct questions, not conflated.
- [ ] Any marginal or flagged result re-run with independent seeding before being treated as a genuine finding.
- [ ] Sensitivity/robustness explicitly checked for at least the most load-bearing conclusions — does the result survive a different seed, a different sample size?
- [ ] Replication attempted via a genuinely independent draw (different seed, ideally different implementation), not a mechanical re-run of identical code and inputs.
- [ ] Sampling uncertainty (statistical) and modeling uncertainty (the Markov assumption, or equivalent structural assumptions elsewhere in the pipeline) kept explicitly distinct, with each addressed by its own appropriate technique.
