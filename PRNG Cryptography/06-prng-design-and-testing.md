## 1. Random Number Generators

### 1.1 The design-family landscape

Every PRNG design in the ARX space falls into one of a small number of structural families, each with a distinct primary use case and a distinct set of design tradeoffs:

- **Counter-based generators** (Threefry, Philox — `02` §2.5): compute output(counter, key) directly, statelessly, via a fixed number of ARX (or, for Philox, multiplication-based) rounds — no sequential state update at all. **Primary advantage**: perfect parallelizability (any output can be computed independently, in any order, on any core/GPU-lane) and trivial "seeking" (jump directly to output N without computing outputs 1..N-1). **Primary use case**: large-scale parallel scientific/simulation computing, not general-purpose cryptographic key generation (per `02`'s explicit caveat about their lighter adversarial-cryptanalysis scrutiny relative to mainstream CSPRNGs).
- **Permutation-based generators**: apply a fixed, unkeyed (or rarely-rekeyed) permutation (Sparkle, Xoodoo, an Ascon-style permutation) repeatedly to an evolving state, extracting output bits at each step — structurally identical to the sponge/duplex "squeeze" operation (general-cryptography report, Part `02` §4.2), making sponge-based hash functions and sponge-based PRNGs close structural cousins built from the same underlying primitive.
- **Stream-cipher generators**: run a stream cipher (ChaCha20 being, by a wide margin, the dominant real-world choice) in a mode specifically designed for the *generator* role rather than the *encryption* role — the key distinction, covered in 1.3 below, being how the generator handles state exposure/compromise recovery, since a pure stream cipher's keystream, if the internal state is ever exposed, offers no forward protection for future outputs the way a well-designed PRNG's reseeding/rekeying discipline does.
- **Hash-based generators**: build a generator around repeated hashing of an accumulating state (Hash_DRBG, per the general-cryptography report's Part `04` §2.3) — less prominent in the specifically-ARX-focused literature than the stream-cipher and permutation-based families, since the hash function itself, if it's a sponge (Keccak/Ascon-style), is really a special case of the permutation-based family above; if it's Merkle–Damgård-based (SHA-2-style), it's not ARX at all in the internal-nonlinearity sense this report cares about.
- **Sponge generators**: the specific case of a permutation-based generator built explicitly around the absorb/squeeze sponge API (general-cryptography report, Part `02` §4.2) — able to absorb fresh entropy (reseed) and squeeze output in an interleaved, flexible pattern, making the sponge framework a particularly natural fit for a generator that needs to support both continuous output extraction *and* periodic reseeding within one unified API, exactly the flexibility Xoodyak's "Cyclist" mode (`02` §2.6) was explicitly designed to provide.

### 1.2 Fast-key-erasure — the current best-practice design pattern

**Fast-key-erasure RNG design** (the term and the specific construction most closely associated with Daniel J. Bernstein's public design notes, and the underlying approach adopted by the modern Linux kernel RNG per this conversation's general-cryptography report, Part `04` §2.3) is the current, field-converged answer to a specific, important design question: **how should a stream-cipher-based generator update its internal state to maximize forward secrecy while minimizing the performance cost of doing so?** The core idea: rather than generating a large batch of output from a fixed key and only rekeying occasionally (which leaves a long window during which state compromise reveals *all* prior output generated under that key, and, more subtly, may still allow *future* output prediction if the compromise happens mid-batch), a fast-key-erasure design **generates just enough keystream to produce (a) the requested output and (b) a fresh replacement key, immediately overwrites the old key with the new one in memory, and discards the old key material entirely** — meaning even an attacker who fully compromises the generator's state at some instant learns *nothing* about output already delivered before that instant (true forward secrecy, at essentially the cost of one extra block of ChaCha20 output per rekey operation, i.e., very cheap) and, given fresh entropy input, recovers proper behavior going forward. This pattern is now considered the field's best-practice baseline for any new stream-cipher-based (and, by natural extension, any ARX-based) generator design, and a new PRNG proposal that doesn't explicitly address forward-secrecy via some equivalent mechanism should be considered incomplete by current standards.

### 1.3 Forward secrecy, backward secrecy, and fork safety

- **Forward secrecy** (as just described, 1.2): compromising the generator's *current* state should not reveal *previously* generated output.
- **Backward secrecy** (also called "future secrecy" or "post-compromise security" in the general-cryptography report's Signal-ratchet terminology, Part `05` §1.4): compromising the generator's *current* state should not let an attacker predict *future* output, **provided fresh entropy is subsequently mixed in** — this is a genuinely different, and generally harder-to-achieve-unconditionally, property than forward secrecy, since without *new, unpredictable* entropy input, an attacker who's compromised the full internal state has, definitionally, everything needed to compute all future outputs deterministically (no PRNG can achieve backward secrecy purely from its own internal computation with zero new entropy — this would be a mathematical contradiction, since the generator's future behavior would then be a deterministic function of already-known state). A responsible generator design should therefore couple its fast-key-erasure forward-secrecy mechanism with an explicit, clearly-specified reseeding/entropy-remixing schedule (per 1.4 below) as the actual mechanism delivering backward secrecy in practice.
- **Fork safety**: a specific, easily-overlooked failure mode relevant to virtualized/containerized deployment — if a process (or an entire VM) is snapshotted and later resumed or cloned (a container fork, a VM snapshot restore, a `fork()` system call in a Unix process), and the generator's internal state is naively copied along with the rest of the process state, **both the original and the forked copy will subsequently produce identical output streams from that point forward** unless the generator is specifically designed (or the deploying system specifically intervenes) to detect and recover from this — a real, historically-documented failure class (general-cryptography report, Part `04` §2.4's Debian OpenSSL discussion is a related, if distinct, cautionary tale about entropy-source failures generally) and part of why modern OS-level RNGs (2.5 below) go out of their way to mix in fork-detection-relevant signals (process ID, boot-time counters, explicit `getrandom()`-style reseed-on-fork hooks) rather than relying purely on the generator's own internal ARX state evolution to handle this case.

### 1.4 Reseeding, entropy accumulation, and output extraction

**Reseeding** — periodically mixing genuinely fresh entropy (general-cryptography report, Part `04` §2.1–2.2) into the generator's internal state — is what actually delivers backward secrecy (1.3 above) in practice, and a responsible design specifies (a) how much fresh entropy is required per reseed, (b) how often reseeding occurs (time-based, output-volume-based, or both), and (c) how the fresh entropy is *combined* with existing internal state (a proper extractor/mixing function, per the general-cryptography report's leftover-hash-lemma discussion, Part `04` §2.2 — not a naive XOR, which can fail to properly "absorb" low-quality or partially-predictable entropy inputs). **Entropy accumulation** across multiple, potentially-weak sources (Fortuna's multi-pool design, general-cryptography report Part `04` §2.3, is the canonical reference architecture) is directly relevant to any ARX-based generator's *entropy-input* stage specifically, even though the generator's *output-stretching* stage (the ARX permutation/cipher itself) is a separate design concern. **Output extraction**: how raw generator state is converted into delivered output bits — for a sponge-based design, this is simply the "squeeze" phase; for a stream-cipher-based design, it's the raw keystream output, subject to the fast-key-erasure discipline of 1.2.

### 1.5 State compromise recovery — synthesized

Putting 1.2–1.4 together: a **responsibly-designed 2026-era ARX-based PRNG** should be explicitly evaluated (and documented, for publication purposes) against all of: forward secrecy (via fast-key-erasure or equivalent), backward secrecy (via a specified reseeding schedule and proper entropy-mixing function), and fork safety (via either an internal mechanism or explicit deployment-level guidance) — treating all three as *separate, individually-required* properties, not as automatically implied by "uses a cryptographically strong ARX permutation internally," since (as 1.3 makes explicit) none of these properties follow automatically from the underlying permutation's cryptographic strength alone — they are properties of the *surrounding generator construction*, not of the permutation itself, exactly analogous to how a strong block cipher doesn't automatically make every mode of operation built from it secure (general-cryptography report, Part `02` §5).

### 1.6 Modern operating-system RNGs

- **Linux kernel RNG**: as covered in the general-cryptography report (Part `04` §2.3), the modern Linux RNG's core CSPRNG mechanism is ChaCha20-based, explicitly incorporating fast-key-erasure-style discipline, jitter-entropy software-based entropy collection, and fork/VM-snapshot-aware reseeding hooks — the field's most widely-deployed, most heavily-scrutinized real-world instance of essentially every design principle in this section combined into one production system, and worth studying directly (via its public kernel source and the LWN/kernel-mailing-list design discussions around its ChaCha20 transition) as the single best "worked example" available.
- **Windows RNG** (`BCryptGenRandom`/CNG): NIST SP 800-90A-compliant DRBG mechanisms integrated with hardware entropy sources, per the general-cryptography report's Part `04` §2.3 coverage — less directly ARX-specific in its public design documentation than Linux's ChaCha20-based approach, but conceptually addressing the same set of properties.
- **BSD/macOS lineage**: historically Yarrow-based, evolved toward Fortuna-family designs over time (general-cryptography report, Part `04` §2.3) — the specific ARX-vs-other-primitive choice for the underlying stretching function varies by implementation and is less uniformly documented/publicized than Linux's explicit ChaCha20 commitment.

### 1.7 Research gaps

Genuine, current open areas specifically at the ARX/PRNG intersection: (a) **formal, unified security definitions and proofs for the fast-key-erasure pattern specifically** — while the construction is now widely deployed and generally trusted based on strong design-rationale arguments, a fully worked-out, widely-agreed formal security proof (in the sense of `05` §3's game-based/concrete-security framework) treating forward secrecy, backward secrecy, and fork safety *jointly*, for a fast-key-erasure ChaCha20-based construction specifically, is less mature in the published literature than the construction's real-world deployment maturity would suggest — a real, tractable, and directly impactful research target flagged again in `09`; (b) **sponge-based generator formal treatment specifically** — while sponge-based hash/AEAD security proofs (via the ideal-permutation/indifferentiability framework, `05` §3.2–3.3) are mature, the *generator-specific* additional properties (fork safety, specifically) are less thoroughly treated in the sponge-generator literature than in the stream-cipher-generator literature; (c) **counter-based generators' (Threefry/Philox) adversarial cryptanalysis specifically** — per `02` §2.5's caveat, these remain comparatively under-scrutinized from a genuine cryptographic-adversary perspective relative to their statistical-quality scrutiny, a real, acknowledged, and directly approachable gap for a researcher with both the ARX-cryptanalysis toolkit from `04`–`05` and an interest in the parallel-computing use case specifically.

## 2. Randomness Evaluation

### 2.1 The test suites

- **NIST STS (SP 800-22)**, **Dieharder**, **TestU01** (including its demanding **BigCrush** battery and lighter **SmallCrush**/**Rabbit** batteries for faster, less exhaustive screening), **PractRand**, and the older, simpler **ENT** utility: covered at the general-cryptography level in this conversation's earlier report (Part `04` §2.5); the ARX-specific point worth adding here is that **essentially every ARX-based PRNG design paper in the current literature reports PractRand and/or TestU01/BigCrush results as standard, expected evidence** — specifically because ARX-based generators (ChaCha-derived designs especially) are held to a comparison standard set by ChaCha20's own extremely strong, extensively-verified PractRand/BigCrush performance, making these test suites' output a near-universal, standardized "table stakes" comparison point in any new ARX-PRNG publication, in a way that's somewhat more specifically expected in this sub-literature than in general CSPRNG-design writing.

### 2.2 Interpretation and the central limitation — restated with ARX specificity

The general-cryptography report's Part `04` §2.5 core finding applies with full force here and bears direct restatement in this ARX-specific context, since it is arguably *the* single most important thing for a new researcher in this exact space to internalize early: **passing PractRand/TestU01/BigCrush demonstrates statistical uniformity, not cryptographic unpredictability.** A generator built from a cryptographically weak (but well-diffusing) ARX permutation can pass every standard statistical test suite while remaining fully predictable to an adversary who knows (or can efficiently recover) the internal state or key — because these test suites have no adversarial model at all; they simply check whether the *output distribution* deviates measurably from uniform under a battery of statistical hypotheses, which is a categorically different question from "can a computationally-bounded adversary, given some outputs and unlimited computation up to a stated bound, predict other outputs or recover the key." **Extraction bias and output-conditioning interactions with this limitation**: a generator that applies a strong conditioning/extraction step *after* a weak underlying process can produce statistically excellent output despite the weak underlying process — meaning strong test-suite results say even less about the *underlying ARX permutation's* cryptographic quality specifically when a separate conditioning step is also present, an important, specific methodological trap (measuring the wrong layer of the system) worth calling out explicitly.

### 2.3 Internal state vs. output testing

A closely related, frequently-conflated methodological distinction: testing a generator's **output stream** (what essentially every standard test suite does) is a fundamentally different activity from testing (or formally analyzing) the **internal state-update function's** cryptographic properties (the ARX permutation's own differential/linear/diffusion properties, per `03`–`05`) — a generator can have excellent output-stream statistical properties while its internal state-update function has real, cryptanalytically-exploitable weaknesses that simply haven't yet been found by the *specific* statistical tests being run (since, per 2.2, statistical tests aren't designed to find that kind of weakness at all). **The correct, current-best-practice methodology is therefore two-layer, not one-layer**: (a) subject the *internal ARX permutation/round function* to the full cryptanalytic evaluation toolkit of `04`–`05` (differential/linear/RX/differential-neural trail search, diffusion metrics), exactly as if it were a standalone permutation or cipher being evaluated for its own sake, and (b) *separately*, subject the *complete generator construction's output* to statistical testing (PractRand/BigCrush) as a sanity-check/regression-testing layer, not as the primary security evidence. Reporting only (b) without (a) is a real, documented, and — per `08` — commonly-cited methodological gap in independent (non-peer-reviewed) PRNG proposals specifically.

### 2.4 Common mistakes and historical failures

- **Mistaking test-suite passage for cryptographic security** (2.2 above) — the single most commonly repeated mistake in this specific sub-area, appearing in essentially every retrospective discussion of amateur/independent PRNG design the field has produced.
- **The Dual_EC_DRBG episode** (general-cryptography report, Part `04` §2.4) as the canonical historical illustration: a backdoored generator whose output is, by the backdoor's very design requirement, statistically indistinguishable from random to anyone without the secret trapdoor relationship — meaning it would pass every standard test suite in this section with no anomaly whatsoever, making it the field's sharpest possible illustration of exactly why statistical testing cannot substitute for cryptographic/structural security analysis.
- **Testing only the final output stream of a *composed* system** (a stream cipher wrapped in additional application-level post-processing, say) and attributing strong results to the underlying cipher specifically, when the post-processing layer may be doing some or all of the actual "whitening" work — the layer-conflation trap named in 2.2–2.3.
- **Under-sampling relative to the test's actual sensitivity threshold**: PractRand specifically is designed to test at very large output volumes (its whole value proposition, per the general-cryptography report's Part `04` §2.5 coverage, is sensitivity to flaws that only manifest after enormous amounts of output) — reporting only a small-sample PractRand run and treating a "no anomalies found" result at that sample size as strong evidence, when the specific flaw class under concern might only manifest at a much larger sample size, is a real, specific instance of the general "insufficient statistical power" mistake, worth calling out with PractRand-specific detail since this is exactly the tool where sample-size-to-sensitivity tradeoffs are most explicitly documented and most commonly mishandled by less experienced researchers.
