## 1. ARX Design Principles — How Experts Actually Design These Systems

### 1.1 The round function as the unit of analysis

Every ARX design is built by repeating a **round function** (or, for stream ciphers/permutations organized around smaller sub-units, a **quarter-round** or **half-round**) a fixed number of times. The design process is not "invent a round function, then figure out how many rounds are needed" as a two-stage sequential process in practice — the two co-develop, because round-function *strength per round* (measured via the automated-search tooling of `05`) directly determines the round *count* needed for a target security margin, and round count directly determines performance, so real design is an iterative optimization across (round-function structure, round count) jointly, not a waterfall process. This is the single most important practical-methodology point in this file: **a round function isn't "done" until you know its per-round differential/linear probability bound, and you don't know that until you've built the automated-search model** — Part `05`'s tooling is not a post-hoc verification step bolted onto design; it is part of the design loop.

### 1.2 Quarter rounds, half rounds, and permutation structure

**ChaCha's quarter round** is the canonical example worth internalizing precisely, because nearly every subsequent design discussion in the field references it as the baseline comparison point:

```
a += b; d ^= a; d <<<= 16;
c += d; b ^= c; b <<<= 12;
a += b; d ^= a; d <<<= 8;
c += d; b ^= c; b <<<= 7;
```

Four (addition, XOR, rotation) triples, operating on four 32-bit words (a, b, c, d) drawn from ChaCha's 16-word state. A full ChaCha round applies this quarter-round operation **four times in parallel** to four independent groups of state words — first to the four *columns* of the 4×4 state grid (a "column round"), then, in the next round, to four *diagonals* (a "diagonal round") — alternating column and diagonal rounds across the cipher's full round count (20 for ChaCha20). This column/diagonal alternation is precisely the "lane interaction" mechanism flagged in `01`, §2.7: columns alone would never mix data between columns, so diagonal rounds are structurally required to achieve full-state diffusion in a small number of rounds. **Salsa20's round structure** achieves the analogous goal via a slightly different quarter-round definition and a "column round then row round" alternation rather than ChaCha's "column then diagonal" — a real, if second-order, structural difference between the two designs, and part of why ChaCha achieves faster diffusion per round than Salsa20 despite both being close relatives (this is a frequently-tested piece of comparative-design knowledge in the field, and the reason Bernstein's own ChaCha design rationale explicitly frames it as a diffusion-rate improvement over Salsa20, not merely a stylistic variant).

### 1.3 Mixing layers, state layout, and register pressure

**State layout** — how a design's total state is partitioned into words, and which words interact in which operations — is a first-class design decision with direct implementation consequences. A 16-word (512-bit) state like ChaCha's maps naturally onto **four 128-bit SIMD registers** (each holding four consecutive 32-bit words) on AVX2/NEON-class hardware, meaning the *entire quarter-round-batch* structure can be computed as vector operations across the whole state simultaneously — this is not an implementation-detail afterthought but a direct consequence of the design's word count and grouping having been chosen with SIMD lane counts in mind. **Register pressure** — whether a design's per-round working set fits within a target architecture's available general-purpose or SIMD registers without spilling to memory — is a genuine, if unglamorous, performance-determining design consideration: a design requiring more live state than fits in registers forces memory traffic every round, which can dominate real-world cycles-per-byte figures regardless of how few arithmetic operations the round function uses on paper. **Instruction scheduling and pipeline utilization**: modern CPUs execute independent instructions out-of-order and in parallel across multiple execution ports; a round function with long, strictly sequential dependency chains (each operation waiting on the previous one's result) underutilizes this parallelism, while a round function structured so that multiple independent operations can be issued simultaneously (as ChaCha's four parallel quarter-rounds within a column/diagonal round explicitly are) achieves substantially better real-world throughput than raw operation-count would suggest — **this is exactly why ChaCha's four-way-parallel quarter-round structure within each round is a deliberate performance-engineering decision, not just a diffusion-engineering one**, and a clean illustration of security-relevant design and performance-relevant design being the same design decisions viewed from two angles, not separate concerns to trade off against each other.

### 1.4 Wide states vs. narrow states

A **wide-state** design (Xoodoo's 384-bit state, Keccak's 1600-bit state) has more "room" to maintain security margin against generic attacks (larger state generally means a larger gap between the design's claimed security level and the state size itself, giving more headroom against birthday-bound and related generic attacks on the permutation as a whole) but costs more per-round computation and per-round memory/register footprint. A **narrow-state** design (ChaCha's 512-bit state is comparatively narrow relative to some sponge permutations; Speck32/64's 32-bit total state is extremely narrow, being a research/toy-scale variant specifically) is cheaper per round but has correspondingly less generic-attack headroom, requiring the design to lean more heavily on round count and round-function strength (rather than raw state size) to achieve its target security level. This tradeoff is explicit and quantified in essentially every design's own security-margin documentation, and is a first design-stage decision (state width) that constrains everything downstream (achievable round count for a given performance target, generic-attack security level).

### 1.5 SIMD friendliness and portable optimization as design-stage decisions

Restating `01`'s point with design-process specificity: a design intended for high-throughput software deployment should be architected, from the state-layout stage onward, so that its natural parallel structure (multiple independent lanes/quarter-rounds/branches) maps cleanly onto common SIMD register widths (128-bit SSE/NEON, 256-bit AVX2, 512-bit AVX-512) — this is exactly the reasoning behind ChaCha's four-quarter-round-per-round structure and behind BLAKE3's explicit, from-scratch redesign around a Merkle-tree structure specifically for multi-core/SIMD parallelism (covered in 2.3 below). A design that achieves excellent round-function security properties but has an inherently serial, hard-to-parallelize structure (a design where round i+1 depends on the *complete* output of round i with no internal parallelism) will underperform in software regardless of its cryptanalytic strength, and "portable optimization" in the field's practical sense means writing a reference implementation that a compiler can auto-vectorize reasonably well *even without* hand-written SIMD intrinsics — a genuine, tested property good ARX reference implementations are held to, not an incidental nicety.

## 2. Case Studies

For each design: goals, round structure, state layout, performance, security status, and the lessons-learned framing your outline specifically requested.

### 2.1 Salsa20 (Bernstein, 2005, eSTREAM portfolio)

**Goals**: a fast, simple, side-channel-resistant-by-construction stream cipher, explicitly motivated by table-lookup-based AES's cache-timing weaknesses. **Round structure**: a 4×4 32-bit-word state (constants, key, counter, nonce arranged in a fixed grid), updated via alternating "column rounds" and "row rounds," each applying Salsa20's quarter-round (a slightly different operation-and-rotation-constant sequence than ChaCha's) to four words at a time; the full cipher runs 20 rounds (Salsa20/20), with 8- and 12-round reduced variants (Salsa20/8, Salsa20/12) offered as explicit, named, faster-but-less-conservative options — an unusually transparent design choice, giving cryptanalysts named targets to attack at multiple security/performance points simultaneously, which arguably *accelerated* the field's overall Salsa/ChaCha cryptanalysis literature by giving researchers weaker variants to practice techniques on before attacking the full cipher. **Performance**: excellent on general-purpose CPUs; became the direct basis for the eSTREAM competition's software portfolio selection. **Security status as of 2026**: full Salsa20/20 remains unbroken in any practical sense; the best published attacks (per this report's search record) reach Salsa20/8 at roughly 2^186 time complexity — far beyond any feasible computation, meaning even the deliberately-weakened 8-round variant is not practically broken, only theoretically distinguished from random with a complexity figure well outside real-world reach. **Lessons learned**: offering multiple explicitly-named reduced-round variants as public cryptanalysis targets is a genuinely useful field practice that ChaCha, Speck, and Simon all later adopted; Salsa20's row/column (rather than ChaCha's column/diagonal) diffusion structure achieves full diffusion slightly slower than ChaCha's, a real, if modest, structural lesson that directly motivated ChaCha's redesign.

### 2.2 ChaCha (Bernstein, 2008)

**Goals**: explicitly, per Bernstein's own design note, improve Salsa20's diffusion-per-round without sacrificing performance. **Round structure**: covered in full detail in 1.2 above — the column/diagonal quarter-round alternation. **State layout**: 4×4 grid of 32-bit words (4 fixed constants, 8 key words, a counter, 3 nonce words in the IETF variant — RFC 8439's layout differs slightly from Bernstein's original in the counter/nonce split, a real, practically-important variant distinction implementers must get right). **Performance**: at least as fast as Salsa20 in most benchmarks, with meaningfully better diffusion per round, allowing (in principle, though ChaCha20's standardized round count matches Salsa20's 20 rather than being reduced to exploit this margin) a stronger effective security margin at the same round count. **Security status as of 2026**: best published attack reaches **7.5 of 20 rounds** (Xu, Xu, Tan, Qi, ToSC 2024, building on Bellini et al.'s ToSC 2023 two-bit-difference differential-linear distinguisher and Beierle, Leander, Todo's CRYPTO 2020 3.5-round differential; Flórez-Gutiérrez & Todo's EUROCRYPT 2025 "bit puncturing" technique further improved on the PNB (Probabilistic Neutral Bits) methodology underlying essentially this entire attack line) — a genuinely active, incrementally-advancing research thread through 2025, but one that remains **12.5 rounds short of the deployed cipher**, meaning ChaCha20 as used in TLS 1.3/WireGuard/Signal is not remotely threatened. **Lessons learned**: ChaCha is the field's best-studied live example of "how much cryptanalytic progress against a real, deployed cipher looks like in practice" — steady, single-digit-round-fraction improvements accumulating over nearly two decades via an evolving toolkit (from hand-derived PNBs in 2008 to MILP-boosted differential-linear distinguishers by 2023, per Coutinho & Peyrin's ToSC 2023 "Boosting differential-linear cryptanalysis of ChaCha7 with MILP") — exactly the trajectory a new ARX design's proposer should expect and plan margin against, not a one-off curiosity.

### 2.3 BLAKE2 and BLAKE3

**BLAKE2** (Aumasson, Neves, Wilcox-O'Hearn, Winnerlein, 2012): a from-scratch-optimized descendant of the SHA-3-finalist BLAKE (itself built around a ChaCha-derived core function called G, applied within a wide, HAIFA-mode-influenced iterated compression function), explicitly designed to be **faster than MD5 in software while matching SHA-3-level security margins** — a genuinely unusual, explicit dual goal (beat an insecure-but-legacy-fast hash on speed, while matching a secure-but-newer hash on security) that shaped nearly every design decision, including using ChaCha's quarter-round-derived G function specifically for its favorable SIMD/performance properties. **BLAKE3** (Aumasson, O'Connor, Neves, Winnerlein, 2020): a more radical restructuring, replacing BLAKE2's sequential Merkle–Damgård-style chaining with a **Merkle-tree internal structure**, explicitly to enable **massive parallelism** — independent tree nodes can be hashed concurrently across cores and SIMD lanes with no serial dependency, a direct, deliberate exploitation of the "SIMD-friendliness as a design-stage decision" principle from 1.5 above, at the acknowledged cost of a somewhat more complex specification than BLAKE2's simpler linear chaining. **Security status**: both remain unbroken in any practically-relevant sense; BLAKE3's newer, less-multi-decade-scrutinized status (relative to, say, SHA-2) is an openly acknowledged, if generally low-weighted, consideration for the most conservative deployment contexts. **Lessons learned**: BLAKE3 is the cleanest current illustration in the entire ARX literature of "redesign the *structure*, not just the round function, when the performance bottleneck is architectural (lack of parallelism) rather than per-operation cost" — a lesson equally applicable to future PRNG and permutation design, covered again in `06`.

### 2.4 SipHash (Aumasson, Bernstein, 2012)

**Goals**: not a general-purpose hash function or stream cipher at all, but a fast, **short-output keyed PRF specifically for hash-table/hash-flooding-attack resistance** — defending against algorithmic-complexity denial-of-service attacks where an adversary crafts inputs that all collide under a hash table's non-keyed hash function, degrading O(1) lookups to O(n). **Round structure**: an extremely compact ARX permutation (four 64-bit words, add-rotate-XOR operations directly descended from ChaCha's quarter-round lineage) run for a small, tunable number of "compression" rounds per input block and "finalization" rounds at the end (the canonical SipHash-2-4 naming denotes 2 compression rounds, 4 finalization rounds). **Performance**: extremely fast for short inputs specifically, which is exactly its target use case (hash-table keys, not bulk data). **Security status**: unbroken as a keyed PRF at its recommended parameters; near-universally adopted as the default hash-table hash function across many major language runtimes and standard libraries specifically because of its hash-flooding resistance combined with its speed. **Lessons learned**: SipHash is the field's clearest illustration that "ARX design principles" apply well below full-cipher/full-hash-function scale — a *tiny*, narrowly-scoped ARX construction, rigorously analyzed for its specific, narrow security goal (PRF security against a specific class of adversary), can be exactly the right tool, and is a useful counter-example to any assumption that ARX research is only about building the next general-purpose cipher.

### 2.5 Threefry and Philox (Salmon, Moraes, Dror, Shaw, 2011 — "Random123" family)

**Goals**: **counter-based pseudorandom number generation** for large-scale parallel/scientific computing (Monte Carlo simulation, GPU-based random number generation), where the defining requirement is that **any output can be computed independently and in parallel from a (counter, key) pair with no sequential state dependency** — a fundamentally different design goal from a stream cipher's sequential-keystream generation, covered further in `06`. **Threefry** adapts the ARX-based Threefish block cipher (from the Skein SHA-3 candidate) into counter mode as a PRNG; **Philox** instead uses **multiplication** (not addition) as its primary nonlinear operation, making it, notably, **not strictly ARX** despite frequently appearing in the same comparative literature — a distinction precisely analogous to the Ascon/Sparkle non-ARX-vs-ARX distinction flagged in `01`, worth getting right for the same reasons. **Performance**: both are extremely fast and, critically, **embarrassingly parallel by design** — the counter-based structure means generating the Nth output requires no computation of outputs 1 through N-1, ideal for GPU/SIMD-massive-parallel contexts. **Security status**: both pass extensive randomness testing (PractRand, TestU01) at their recommended round counts and are widely used in scientific-computing contexts; their *cryptographic* (not just statistical) security margin has received less adversarial cryptanalytic attention than mainstream cipher-derived PRNGs, an important, explicitly-flagged caveat — **Threefry/Philox are designed and evaluated primarily for statistical quality at scale, not necessarily to the same adversarial-cryptanalysis standard as a CSPRNG intended for key generation**, and using them in a security-critical (not merely simulation-quality) context without independently verifying this is a real, named category of mistake covered in `08`.

### 2.6 Xoodoo and Xoodyak (Daemen, Hoffert, Peeters, Van Assche, Van Keer — the Keccak-team's follow-on lightweight effort)

**Goals**: a compact, efficient permutation (Xoodoo, 384-bit state, arranged as a 3×4×32-bit lane structure) intended to bring Keccak-style sponge/duplex construction benefits to a genuinely lightweight footprint, wrapped into a full lightweight cipher suite (Xoodyak, a NIST Lightweight Cryptography competition second-round candidate) providing AEAD, hashing, and a "Cyclist" mode supporting flexible duplex-based protocol construction beyond simple AEAD. **Round structure**: Xoodoo's round function uses XOR, bitwise rotation, and — notably — **AND** as its nonlinear operation, not addition, making it (as flagged in `01`) properly classified as **AND-RX rather than strictly ARX**; this is a meaningfully different nonlinearity source from addition's carry-chain-based behavior, with its own distinct differential/linear analysis (closely related to, but not identical to, Simon/Simeck's AND-RX analysis, covered in 2.9 below). **Performance**: highly competitive in both hardware and software for its target lightweight niche. **Security status**: Xoodoo/Xoodyak reached NIST's Lightweight Cryptography competition's later rounds (though ultimately Ascon, not Xoodyak, was selected) and remains actively studied; no practical break exists. **Lessons learned**: Xoodoo/Xoodyak's competition trajectory alongside Sparkle and Ascon is a genuinely instructive real-world data point that a formally-reasoned, well-analyzed permutation (whether AND-RX like Xoodoo or ARX like Sparkle) does not automatically win a standardization competition even absent any cryptanalytic weakness — implementation footprint, API flexibility (Xoodyak's Cyclist mode was explicitly praised for its protocol-construction flexibility), and comparative-evaluation-committee judgment calls all factor in, a real-world-process lesson directly relevant to `08`'s reviewer/committee-mindset material.

### 2.7 The Ascon permutation (Dobraunig, Eichlseder, Mendel, Schläffer — NIST SP 800-232, finalized August 13, 2025)

Covered here specifically because of its constant comparative presence in ARX-adjacent discussions, despite **not being an ARX design**, per `01`'s explicit flag: Ascon's permutation operates on a 320-bit state (five 64-bit lanes) via a round function combining a fixed 5-bit S-box (applied bitsliced across the five lanes, giving it much of ARX's SIMD/bitslice-friendly software performance character despite being a genuine substitution, not an addition) with a linear diffusion layer per lane. **Why it's discussed alongside ARX designs**: it was Sparkle/Alzette's, Xoodyak's, and TinyJambu's (2.10 below) direct standardization-competition rival, sharing the same lightweight-cryptography target niche and much of the same evaluation criteria (hardware/software footprint, side-channel posture), even though its internal nonlinearity source is structurally an SPN-family S-box, not addition. **Status**: the winning, finalized NIST lightweight-cryptography standard (SP 800-232, August 13, 2025), specifying Ascon-AEAD128, Ascon-Hash256, Ascon-XOF128, and Ascon-CXOF128, supporting up to 16 rounds of the underlying permutation with implementation options (truncation, nonce masking) added during the standardization process beyond the original competition submission. **Lessons learned for ARX researchers specifically**: Ascon's victory over Sparkle (ARX) and Xoodyak (AND-RX) in a competition where all three were serious, well-analyzed, genuinely competitive candidates is the report's clearest illustration that **ARX is a strong, well-motivated design choice, not an inevitable or uniquely-correct one** — a researcher designing a new ARX permutation should understand precisely and specifically *why* they're choosing ARX over the SPN-sponge-hybrid alternative Ascon represents (side-channel posture without hardware acceleration, software-first deployment context, SIMD throughput priorities) rather than treating ARX as a default.

### 2.8 NORX (Aumasson, Jovanovic, Neves — CAESAR competition candidate, 2014)

**Goals**: a parallel, high-performance AEAD scheme built around an ARX-based sponge/duplex permutation, explicitly designed with **built-in native parallelism** (a "NORX-P" parallel mode, distinct from the sequential single-lane baseline) as a first-class feature, and explicitly avoiding lookup tables and secret-dependent branches (constant-time by construction, per `01`'s core ARX rationale) as a stated anti-side-channel design goal. **Status**: reached the CAESAR competition's third round but was **withdrawn by its own designers in 2019**, before the competition concluded, over concerns related to potential (undisclosed at the time of withdrawal, per the designers' own public statement) government-influence pressure on cryptographic standards generally — an unusual, non-cryptanalytic withdrawal reason worth knowing specifically because it's a real illustration that a design can be withdrawn from consideration for reasons entirely unrelated to any weakness being found in it, a genuinely different "why designs don't survive" mechanism than every other case study in this file. **Lessons learned**: NORX's ARX-based-permutation-plus-parallel-mode structure directly influenced later parallel-AEAD design thinking, and its self-withdrawal is a standing reminder that the field's trust dynamics involve institutional and political dimensions (echoing the Dual_EC_DRBG and NIST-curve-provenance discussions in this conversation's earlier general-cryptography report) alongside purely mathematical ones.

### 2.9 Speck and Simon (NSA, 2013)

**Goals**: a matched pair of lightweight block cipher *families* (each spanning many block/key-size combinations, from 32/64 up to 128/256) released simultaneously by the NSA specifically to cover two different optimization targets: **Speck for software performance** (ARX, Feistel-like two-word structure with addition as its nonlinear engine) and **Simon for hardware performance** (AND-RX — bitwise AND, rotation, XOR — chosen specifically because AND gates are extremely cheap in hardware relative to addition's carry-chain circuitry). **Round structure**: Speck's round is strikingly minimal — for the base two-word Feistel-like structure, one rotation, one addition, one XOR with the key, and a swap, repeated for a size-dependent round count; Simon's round is comparably minimal but substitutes AND for addition. **Performance**: both are extremely fast in their respective target domains and became standard academic benchmark targets specifically *because* of their minimalism — their round functions are simple enough that automated-search tooling (`05`) can be applied exhaustively across many round counts, making them the field's most-published-about cryptanalysis targets of the entire post-2013 ARX/AND-RX literature (the MILP/SAT/RX-cryptanalysis search results referenced throughout `04` and `05` overwhelmingly use Speck and Simon as their primary benchmark ciphers for exactly this reason). **Security status**: both remain unbroken at their full specified round counts; the extensive published cryptanalysis (differential, linear, RX-differential reaching 17–24 rounds against various Speck variants, differential-neural distinguishers per `04`) has, cumulatively, mapped their security margins in more published detail than almost any other cipher family in the modern literature, precisely because of their popularity as research targets. **Adoption status and controversy**: NSA's authorship drew immediate, persistent scrutiny (echoing the DES-S-box and Dual_EC_DRBG trust dynamics covered earlier in this conversation) and, notably, **the ISO standardization process rejected Simon and Speck for inclusion in ISO/IEC 29192** (lightweight cryptography) in 2018, reportedly over unresolved concerns about the transparency of the design/security-analysis process, despite no cryptanalytic break being found — a second, distinct (from NORX's) illustration that institutional/trust dynamics, not just cryptanalytic results, determine which designs achieve formal standardization. **Lessons learned**: Speck/Simon are simultaneously the field's most cryptanalytically-productive research targets (precisely because of their minimalism and public research-community-wide focus on them) and a standing case study in how design-team provenance and process transparency affect real-world standardization outcomes independent of technical merit — both lessons matter equally for a 2026 researcher.

### 2.10 LEA (Hong, Lee, Kim, Kwon, et al. — South Korea, 2013)

**Goals**: a fast, software-oriented, purely ARX 128-bit-block cipher developed as a national (South Korean, via KISA) standard, explicitly designed around 32-bit ARX operations for strong performance on general-purpose CPUs. **Round structure**: a four-word ARX round distinct from both Speck's two-word Feistel-like structure and ChaCha's permutation-style structure — closer in spirit to a generalized ARX block-cipher round with per-round-varying rotation amounts. **Status**: standardized in South Korea (KS X 3246) and by ISO/IEC 29192-2:2019 (notably succeeding where Speck/Simon's ISO bid did not); actively studied in the MILP/automated-search literature (referenced directly in the `05` tooling papers this report's search record surfaced — LEA appears as a standard automated-search benchmark target alongside Speck, HIGHT, and ChaCha). **Lessons learned**: LEA's successful ISO standardization, in specific contrast to Speck/Simon's rejection, is worth pairing directly with 2.9 above as a controlled illustration of process/provenance mattering independent of the underlying cryptographic paradigm (both are ARX or ARX-adjacent lightweight ciphers of comparable vintage) — the differentiating factor was institutional and process-transparency, not mathematics.

### 2.11 TinyJambu (Wu, Huang — NIST Lightweight Cryptography finalist)

**Goals**: an extremely minimal, permutation-based lightweight AEAD design targeting the smallest possible hardware footprint among NIST's lightweight-cryptography finalists, built around a simple 128-bit NLFSR (nonlinear feedback shift register)-based permutation rather than a classical wide-block ARX or SPN round structure. **Status**: reached the NIST Lightweight Cryptography competition's final round alongside Ascon, Sparkle, and Xoodyak, but was not selected; remains actively studied for its extreme-minimalism design point specifically. **Lessons learned**: included here (despite sitting somewhat outside strict ARX/AND-RX classification, being NLFSR-based rather than a rotation-based mixing structure) because it represents the *other* extreme of the same design-space tradeoff Speck/Sparkle/Xoodoo/Ascon collectively explore — minimal hardware footprint as the overriding design constraint — and rounds out this report's coverage of what NIST's lightweight-cryptography competition process actually evaluated head-to-head.

### 2.12 Sparkle and Alzette (Beierle, Biryukov, Cardoso dos Santos, Großschädl, Perrin, Udovenko, Velichkov, Wang — CRYPTO 2020 / NIST LWC finalist)

Given full, dedicated treatment because it is this report's clearest illustration of a *provably-margined* ARX design and directly informs `03`'s long-trail-strategy discussion. **Goals**: a family of ARX permutations (Sparkle256/384/512, named by state size in bits) built around a 64-bit ARX-box called **Alzette**, explicitly engineered to achieve a **provable** (not merely empirically-tested) differential/linear security bound via a purpose-adapted version of the wide-trail strategy the designers call the **long-trail strategy** — genuinely novel methodological research contribution in its own right, not just a new cipher. **Round structure**: each Sparkle round applies Alzette (itself a short, fixed 4-step add-rotate-XOR-constant sequence — the paper's own published best 7-round Alzette differential trail probability is 2^-26, an exact, publicly-documented figure) to each 64-bit branch of the state, followed by a linear diffusion layer (the "ℓ" function, itself a small ARX-based mixing operation, feeding branches together) and round-constant injection. **Wrapped constructions**: **Schwaemm** (AEAD, via a Beetle-mode sponge-like construction around the Sparkle permutation) and **Esch** (a sponge-based hash function, Esch256/Esch384). **Performance**: highly competitive in both hardware and software footprint, per the designers' own and NIST's comparative evaluation. **Security status**: no practical break exists; the long-trail-strategy-derived bounds give an explicit, published table of the maximum round count for which any differential/linear attack breaking a b/2-bit security level could conceivably exist, directly analogous in spirit to AES's wide-trail-derived bounds. **Standardization outcome**: reached NIST's Lightweight Cryptography competition final ten (round 3/finalist round) but was **not** the eventual winner — Ascon was selected and finalized as SP 800-232 in August 2025. **Lessons learned — this report's single most important design case study**: Sparkle/Alzette demonstrates conclusively that **a rigorous, provable-margin ARX design is achievable using genuinely novel, ARX-specific proof techniques** (the long-trail strategy is not a trivial restatement of the wide-trail strategy; adapting it to addition's carry-chain-dependent, position-non-uniform nonlinearity was real research), directly rebutting any assumption that ARX designs are inherently limited to empirical, non-provable security claims — and simultaneously demonstrates that **provable security margin alone does not guarantee standardization success**, since Ascon won on the balance of NIST's full evaluation criteria despite Sparkle's comparably rigorous (if structurally different) security case. Any researcher aiming to design a new ARX permutation with serious publication/adoption ambitions should treat the Sparkle/Alzette paper and its long-trail-strategy methodology as required primary-source reading (flagged again in `10`).
