## 1. Implementation

### 1.1 Constant-time programming for ARX specifically

The general principles (avoid secret-dependent branches, avoid secret-dependent memory access, use constant-iteration-count loops, use dedicated constant-time comparison) are covered fully in the general-cryptography report, Part `05` §2.1. **ARX's specific, structural advantage**, restated with implementation precision: because a correctly-written ARX round function contains **no data-dependent array indexing at all** (unlike an SPN's S-box lookup), a straightforward, naive-looking C implementation of ChaCha20's quarter-round is, in fact, *already* constant-time with respect to cache-timing side channels, with essentially no special defensive coding required beyond the ordinary discipline of not accidentally introducing a secret-dependent branch elsewhere in the surrounding code (a nonce-comparison function, an early-exit on a padding check, etc. — none of which are part of the ARX core itself, but are common places for constant-time bugs to creep into an otherwise-correct ARX-based system). This genuinely lowers the implementation-security burden relative to a naive software-AES implementation, though it does **not** eliminate the need for constant-time discipline in the surrounding system entirely, and does **not** address the microarchitectural/transient-execution attack class (1.2 below and general-cryptography report Part `04` §1.5), which operates below the level any source-code-level constant-time discipline can directly control.

### 1.2 Microarchitecture, CPU pipelines, and carry chains

**Instruction latency and throughput**: modular addition, XOR, and rotation are each typically single-cycle-latency, high-throughput operations on modern CPUs (often with throughput of 2–4 independent instances issuable per cycle across multiple execution ports on current out-of-order cores) — meaning an ARX round function's *raw* operation count translates fairly directly and predictably into cycle count, with comparatively little of the "surprising" microarchitectural cost variance a table-lookup-heavy SPN implementation can exhibit (cache-miss penalties, for instance, simply don't apply to ARX's register-only operation sequence). **Carry chains specifically**: while addition itself is single-cycle on modern hardware (the carry-chain computation is fully resolved within the ALU's fixed latency, not something software needs to reason about at the instruction level), the *cryptanalytic* carry-chain behavior discussed throughout `01` and `04` remains entirely a property of the *mathematical* operation, not of any implementation-visible timing variation — worth being precise about, since "carry chain" means two different things in this report depending on context (the cryptanalytically-relevant bit-level carry-propagation structure of `01` §2.2, versus the hardware ALU's internal carry-chain circuit, which is not security-relevant in the same way and does not leak timing information on any modern general-purpose CPU). **Register allocation and instruction scheduling**: covered at the design-principle level in `02` §1.3; at the implementation level, this means writing code (or structuring an implementation to help a compiler generate code) that keeps a round function's live working set within the target architecture's available register file, and that exposes the round function's genuine internal parallelism (independent quarter-rounds, independent lanes) in a form the compiler's instruction scheduler and out-of-order execution engine can actually exploit — sequential-looking source code can sometimes obscure genuine independence that a compiler fails to discover, making explicit, hand-structured parallelism (or explicit SIMD intrinsics, 1.4 below) a meaningful, measurable performance lever beyond what a naive "just write the obvious C code" approach achieves.

### 1.3 Compiler optimization and undefined behavior

Directly paralleling the general-cryptography report's Part `05` §2.2 discussion of UB-driven miscompilation risk (the `memset`-elimination example): ARX implementations face an analogous, ARX-specific risk around **signed-integer overflow**, which is undefined behavior in C/C++ for signed types (though *defined*, wrapping, behavior for unsigned types) — meaning **an ARX implementation must use unsigned integer types for all modular-addition operations**, since using a signed type and relying on wraparound behavior invites a compiler to assume overflow never happens (since it would be UB) and optimize the code in ways that silently break the intended modular-addition semantics; this is a real, specific, easily-overlooked correctness (not just performance or side-channel) bug class specific to ARX implementation, distinct from but analogous in *kind* to the general UB-miscompilation risk covered in the general-cryptography report. Compiler auto-vectorization (1.4 below) is also UB-sensitive in the same way: a compiler is only free to auto-vectorize (or otherwise aggressively reorder/transform) arithmetic that has well-defined semantics under all possible inputs, making strict unsigned-arithmetic discipline doubly important — both for correctness and for enabling the compiler optimizations that give ARX its practical performance advantage in the first place.

### 1.4 SIMD, vectorization, and portable optimization

Restating and extending `02` §1.3–1.5 with concrete implementation detail: a well-structured ARX reference implementation should expose its internal parallelism (multiple independent quarter-rounds/lanes) in a form amenable to **auto-vectorization** by a modern optimizing compiler (GCC/Clang/MSVC's auto-vectorizer can often successfully vectorize a cleanly-written, branch-free, UB-free ARX round loop without any explicit intrinsics), while a **hand-vectorized** implementation using explicit SIMD intrinsics (SSE2/AVX2/AVX-512 intrinsics on x86, NEON intrinsics on ARM) typically achieves meaningfully better real-world throughput than auto-vectorization alone, at the cost of platform-specific code paths and correspondingly more implementation/maintenance/audit burden — the standard real-world tradeoff essentially every serious ARX library (libsodium's ChaCha20 implementations being a widely-cited reference example, per the general-cryptography report's Part `05` §3.3 coverage of libsodium generally) resolves by shipping *both*: a portable, auto-vectorization-friendly generic C reference implementation as the correctness baseline and universal fallback, plus one or more hand-optimized, architecture-specific SIMD implementations selected at runtime (via CPU-feature detection) for platforms where they're available.

### 1.5 Rust, C, and assembly

**C** remains the dominant implementation language for ARX reference implementations and most production libraries, for the same historical/ecosystem reasons covered in the general-cryptography report's Part `05` §2.2, with the same memory-safety caveats applying — though ARX's specific implementation profile (no complex pointer-heavy data structures, mostly straight-line arithmetic over fixed-size buffers) means ARX code is, in practice, somewhat less prone to the classic buffer-overflow/use-after-free bug classes that plague more structurally complex C cryptographic code, without eliminating the risk entirely. **Rust** implementations (RustCrypto's ARX-family crates being the standard reference, per the general-cryptography report's Part `05` §3.3) provide the same compile-time memory-safety guarantees discussed generally in that report, directly applicable here with no ARX-specific caveats beyond the usual `unsafe`-block caveat for any hand-vectorized SIMD intrinsics code (SIMD intrinsics generally require `unsafe` in Rust, since they bypass the type system's normal safety reasoning). **Hand-written assembly** remains used, selectively, for the most performance-critical, most widely-deployed ARX implementations (portions of libsodium's and OpenSSL/BoringSSL's ChaCha20 implementations include hand-tuned assembly for specific high-value targets), generally reserved for cases where compiler-generated code (even with intrinsics) measurably underperforms what a human expert can achieve through direct instruction-level control — an increasingly narrow but non-zero set of cases as compilers have improved.

### 1.6 Reference implementations

A responsible new ARX design's publication should include, as a matter of current expected practice (previewed here, elaborated in `08`): a portable, minimal, auditable **reference implementation** (correctness-focused, not performance-focused — this is the implementation a reviewer or independent researcher should be able to read start-to-finish and verify against the paper's specification directly) *and*, increasingly expected though not universally mandatory, at least one **optimized implementation** demonstrating the design's real-world performance claims are achievable in practice, not merely theoretically implied by operation-count arguments — the Sparkle suite's own published materials (`02` §2.12), explicitly providing both a "universal reference implementation" and separate architecture-tuned optimized versions (their ARMv7M-specific release, for instance), are a good model of this expected dual-deliverable practice.

## 2. Hardware

### 2.1 Portable cryptography vs. hardware-accelerated designs

Restating `01` §1.6's core point with the specific current hardware landscape: ARX's performance advantage is fundamentally a **software-without-dedicated-hardware** advantage. Where genuine hardware acceleration exists and is available, hardware-accelerated alternatives can outperform even well-optimized ARX software — the tradeoff is portability and universality (ARX runs well *everywhere*) versus peak throughput *on specific, accelerated platforms*.

### 2.2 The hardware acceleration landscape, 2026

| Technology | Platform | Relevance to ARX |
|---|---|---|
| **AES-NI** | x86 (Intel/AMD) | Direct hardware acceleration for AES specifically; no ARX-equivalent instruction exists — this is precisely the asymmetry motivating ChaCha20-Poly1305's continued relevance as the "no dedicated hardware needed" AEAD alternative to AES-GCM (general-cryptography report, Part `02` §5.4) |
| **GFNI** (Galois Field New Instructions) | Recent x86 (Intel/AMD) | Accelerates GF(2^8)-based operations (relevant to AES-adjacent and some non-ARX finite-field cryptography); not directly applicable to ARX's addition/rotation/XOR operations, though GFNI-equipped platforms can sometimes accelerate *bitsliced* implementations of designs (including some ARX-adjacent or hybrid constructions) that can be reformulated in terms of the bitwise operations GFNI accelerates |
| **AVX2** | x86 (widespread) | 256-bit SIMD; the current mainstream target for portable-but-fast ChaCha20/BLAKE3-family software implementations, processing 8×32-bit lanes in parallel |
| **AVX-512** | x86 (higher-end/server, increasingly mainstream) | 512-bit SIMD, 16×32-bit lanes; the current highest-throughput mainstream target for ARX software, with correspondingly larger register file easing the register-pressure concerns of `02` §1.3 |
| **ARM NEON** | ARM (essentially universal on modern ARM cores, mobile and server) | 128-bit SIMD; the mobile/embedded-relevant target given ARX's historical mobile-chipset-without-AES-NI motivation (`01` §1.2) remains directly relevant |
| **ARM SVE/SVE2** (Scalable Vector Extension) | Newer ARM server/HPC cores | Variable-width vector length (unlike NEON's fixed 128-bit), an architecturally different SIMD model requiring some implementation-strategy adaptation but conceptually well-suited to ARX's lane-parallel structure |
| **RISC-V Vector (RVV)** | RISC-V (growing adoption) | An emerging, actively-developing target; RISC-V's open-ISA nature and growing adoption in embedded/IoT contexts makes it an increasingly relevant portable-cryptography target, directly overlapping with ARX's traditional lightweight/embedded deployment niche |

### 2.3 Tradeoffs and future hardware trends

The overall, durable pattern this landscape reflects: **AES has a fixed-function hardware fast path on its dominant deployment platform (x86 via AES-NI); ARX designs do not have an equivalent, and instead rely on general-purpose SIMD width growth (AVX2 → AVX-512, NEON → SVE) to keep improving.** This is a genuinely stable, structural asymmetry unlikely to change (no major vendor has signaled plans for a dedicated "ChaCha-NI"-style instruction, since ARX's whole value proposition is *not needing* dedicated hardware), meaning ARX's future performance trajectory is tied to general SIMD-width and core-count trends (favorable, given the industry's continuing investment in wider vector units and RISC-V's growing footprint in exactly the lightweight/embedded space ARX also targets) rather than to any ARX-specific hardware roadmap. This is, if anything, a point in ARX's favor for long-term design planning: a new ARX design benefits automatically from general-purpose hardware trends without needing anyone to build ARX-specific silicon first.

## 3. Benchmarking

### 3.1 How professional cryptographers actually benchmark

**Cycles per byte (cpb)** is the field's standard, near-universal throughput metric — normalizing for CPU clock speed differences across benchmarking platforms in a way raw wall-clock time doesn't, and directly comparable across papers/designs in a way that makes it the expected headline performance number in essentially every ARX design publication. **Latency** (time to produce output from a cold start, relevant for short-message/low-latency use cases like SipHash's hash-table-lookup target) is measured and reported *separately* from **throughput** (steady-state bytes-per-cycle on large inputs), since the two can diverge substantially — a design optimized for bulk throughput (large SIMD batches) may have comparatively poor short-message latency if it can't productively use its full SIMD width on a small input, a real, design-relevant tradeoff (ChaCha's per-block structure handles this reasonably well; some more aggressively batch-oriented designs handle it less well, a genuine point of comparison worth explicitly measuring and reporting, not assuming away).

### 3.2 Energy, memory, and cache behavior

**Energy consumption** is an increasingly reported metric specifically for lightweight/embedded/IoT-targeted designs (directly relevant to the NIST Lightweight Cryptography competition's evaluation criteria discussed throughout `02`), measured via direct hardware power monitoring on target embedded platforms rather than estimated from cycle counts alone, since energy-per-operation doesn't scale purely linearly with cycle count across different instruction types and microarchitectures. **Memory footprint** (both code size/ROM footprint and working-state/RAM footprint) is likewise a first-class reported metric for lightweight-targeted designs specifically — this is precisely one of the axes on which Ascon's SPN-sponge approach and Sparkle/Xoodyak's ARX/AND-RX approaches were head-to-head compared in NIST's competition evaluation (`02` §2.6–2.7, §2.12). **Cache behavior**: for ARX designs specifically, this is largely a non-issue in the sense that there's no secret-dependent cache access pattern to characterize (`01` §1.2, this file §1.1) — but *aggregate* cache footprint (does the working state and code fit comfortably in L1 cache, avoiding unnecessary cache pressure on the surrounding application) remains a relevant, reportable performance consideration distinct from the side-channel question.

### 3.3 Instruction counts and benchmark methodology

Raw **instruction counts** (how many total add/rotate/XOR instructions per byte processed) give a useful, platform-independent, first-order performance estimate usable early in design (before any real implementation exists) — directly computable from a round function's specification and round count, and a standard, expected "back of the envelope" figure to report alongside (not instead of) measured cycles-per-byte. **Methodology, more broadly**: current expected practice includes reporting the specific CPU model/microarchitecture used for benchmarking (results vary meaningfully across microarchitecture generations even within the same vendor/ISA family), the compiler and optimization flags used, whether hyperthreading/SMT and frequency-scaling/turbo-boost were disabled during measurement (both introduce measurement noise a rigorous benchmark should control for), and whether the reported figures are for the portable reference implementation, a compiler-auto-vectorized build, or a hand-tuned SIMD/assembly implementation — conflating these categories (reporting a hand-tuned assembly implementation's cycles-per-byte as if it represented the design's "typical" or reference performance) is a real, specifically-named methodological problem covered further in `08`'s research-mistakes discussion.

### 3.4 Reproducibility and common pitfalls

**Reproducibility**: current best practice (mirroring the general research-methodology expectations covered fully in `08`) is to publish the exact benchmark harness/code alongside the paper, not merely the resulting numbers — letting independent researchers reproduce the specific measured figures on their own hardware, both as a sanity check and as the basis for fair future comparisons by other designs' authors. **Common pitfalls**, specific to ARX benchmarking: (a) benchmarking only on a single, possibly favorable, microarchitecture/platform and presenting the result as representative of "ARX performance" generally, when SIMD-width availability and specific microarchitectural quirks can shift relative rankings meaningfully across platforms; (b) comparing a hand-tuned, heavily-optimized implementation of a new design against an unoptimized *reference* implementation of a competing prior design (an unfair, if sometimes unintentional, apples-to-oranges comparison — flagged explicitly, with this exact framing, in `08`'s "comparing against strawman baselines" named mistake); (c) omitting variance/repeated-measurement statistics entirely, reporting only a single best-case (or unspecified-which-case) cycles-per-byte number, when real benchmark measurement — subject to thermal throttling, OS scheduling noise, and other real-world variance sources — should be reported with some indication of measurement spread (a minimum-of-N-runs or a mean-plus-variance figure), not a single unqualified number.
