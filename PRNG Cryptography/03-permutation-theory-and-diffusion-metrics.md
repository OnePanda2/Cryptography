## 1. Permutation Design Theory

### 1.1 Invertibility and bijectivity

An ARX **permutation** (as distinct from a keyed block cipher) must be a **bijection** on its full state space — every input state maps to exactly one output state, and the mapping is invertible. This falls out for free from the three building-block operations: modular addition is invertible given either operand held fixed (subtraction), rotation is trivially invertible (rotate the other direction), and XOR is self-inverse — so **any well-formed sequence of these operations is automatically a bijection**, with no special design effort required to guarantee it (unlike, say, a hand-designed S-box, where bijectivity must be explicitly verified). This is a genuine, if underappreciated, ARX convenience: designers get invertibility "for free" and can focus entirely on the *cryptographic* quality of the permutation (diffusion, nonlinearity distribution) rather than needing to separately verify structural well-formedness.

### 1.2 Cycle structure

A permutation on a finite set decomposes into disjoint **cycles**; a cryptographically "ideal" permutation should behave, from the perspective of any computationally-bounded observer, statistically indistinguishable from a uniformly random permutation on the same domain — which, among other things, means its cycle-length distribution should match what's expected for a random permutation (a small number of very long cycles is typical for a truly random permutation; suspiciously many short cycles is a red flag suggesting exploitable structure). In practice, cycle-structure analysis is more heavily emphasized for the *keyless permutation* use case (a sponge's underlying permutation, used identically across all invocations with no key) than for a keyed ARX cipher, precisely because a keyed cipher's effective "permutation" changes per key, making population-level cycle-structure statistics less directly meaningful than they are for a single, fixed, unkeyed permutation like Ascon's or Keccak's — a real, if subtle, methodological distinction worth being precise about when designing a new *permutation* (Xoodoo/Sparkle-style, unkeyed, used inside a sponge/duplex mode) versus a new *keyed cipher* (ChaCha/Speck-style).

### 1.3 State evolution and connectivity

A design's **state graph** — modeling which state bits/words can influence which other state bits/words after k rounds — is the formal object underlying every diffusion claim in this file. Full-state connectivity (every output bit potentially depending on every input bit) after a small number of rounds is a *necessary* but far from *sufficient* condition for security: a design can achieve full formal connectivity while still having exploitably-low actual dependency strength on some bit pairs (a real distinction the diffusion metrics in Part 2 below are specifically built to detect, since simple graph-connectivity analysis alone misses it).

### 1.4 The wide-trail strategy and its ARX-adapted descendant, the long-trail strategy

**The wide-trail strategy** (Daemen, Rijmen — the AES design methodology, covered in Part 2 of this conversation's general-cryptography report) gives SPN designs a *provable* bound on the best possible differential/linear characteristic probability, by separately bounding (a) the minimum number of "active" (nonzero-input-difference) S-boxes any nonzero trail must pass through per some number of rounds (a purely linear-algebra/branch-number argument about the diffusion layer, independent of the S-box's specific properties) and (b) the maximum differential/linear probability any single active S-box can contribute (a property of the S-box alone) — multiplying these together gives a provable upper bound on the trail probability for that many rounds, entirely independent of having to enumerate or search actual trails.

**The long-trail strategy** (Beierle, Biryukov, et al., developed specifically for Sparkle/Alzette, CRYPTO 2020) is the direct ARX-adapted generalization: rather than counting "active S-boxes," it counts **active ARX-boxes** (active Alzette instances) per some number of rounds, using an analogous branch-number-style argument about Sparkle's linear diffusion layer (the "ℓ" function), combined with a *separately, empirically-and-analytically established* bound on Alzette's own maximum differential/linear probability (the published 7-round-Alzette bound of 2^-26, referenced in `02`). The key methodological adaptation required, relative to the SPN case: because an ARX-box's (Alzette's) internal probability doesn't have the same simple, small, exhaustively-verifiable table an S-box's differential distribution table gives for free, establishing that per-ARX-box bound required its own dedicated automated-search effort (`05`'s tooling), making the long-trail strategy a genuinely two-part research contribution — the diffusion-layer branch-number argument (relatively directly adaptable from wide-trail reasoning) *and* the ARX-box probability-bound establishment (requiring new, ARX-specific automated search) — worth understanding as two separable pieces of methodology, since a new ARX-box design would need to redo the second part specifically, even if reusing an existing diffusion layer's already-proven branch number.

### 1.5 Markov assumptions

Both classical differential cryptanalysis (Part `04`) and the wide/long-trail provable-bound methodology rest on a **Markov cipher assumption**: that the probability of a multi-round differential trail can be computed as the *product* of each individual round's differential probability, which is only exactly true if each round's input/output difference behaves independently of the specific key/round-constant values in play (an idealized, generally-false-in-detail but practically-well-justified assumption, formalized by Lai, Massey, Murphy in the SPN context and carried over essentially unchanged as a standard, explicitly-stated assumption in the ARX/long-trail literature). Real automated-search tools (`05`) build their trail-probability estimates on this Markov assumption, and **part of a rigorous security evaluation is explicitly checking, via experiment or a more refined model, that the Markov-assumption-derived probability estimate isn't badly wrong for the specific design in question** — a documented, real failure mode (Part `08`) is trusting a Markov-assumption-derived trail-probability bound without any such sanity-check verification.

## 2. Diffusion — Every Standard Metric, and Its Blind Spots

### 2.1 Avalanche effect and the Strict Avalanche Criterion (SAC)

The **avalanche effect**, informally: flipping a single input bit should, after enough rounds, flip approximately half of all output bits, with no obviously-structured pattern in *which* output bits flip. **SAC** (Webster & Tavares, 1985) formalizes this precisely: a function satisfies SAC if, for every single-bit input flip, *each* output bit flips with probability exactly 1/2 (not just "roughly half of output bits flip on average across many trials" — SAC is a per-output-bit, per-input-bit requirement, materially stricter than a loose "avalanche" description suggests). SAC compliance is typically measured empirically, via a **dependency matrix**: for an n-bit-input, m-bit-output function, an n×m matrix where entry (i,j) records the empirical probability (over many random input pairs differing only in bit i) that output bit j flips; a perfectly-SAC-compliant function has every entry equal to exactly 0.5, and real designs are evaluated by how close their empirical dependency matrix comes to this ideal, often visualized directly as a **heatmap** (a standard, expected figure in ARX design papers' diffusion-analysis section).

### 2.2 Bit Independence Criterion (BIC)

A complementary, distinct property (Webster & Tavares, again): given a single input-bit flip, any *pair* of output bits should flip **independently** of each other, not merely each with individual probability 1/2 — a design can satisfy SAC (each output bit individually flips with probability 1/2) while still having output-bit-pair correlations that violate BIC (e.g., output bits j and k might always flip together or never flip together, even though each individually flips exactly half the time) — a genuinely distinct failure mode SAC alone cannot detect, which is exactly why the field evaluates both, not just one.

### 2.3 Branch number

The **branch number** of a linear (or, for the ARX-adapted case, ARX-box-plus-diffusion-layer) component measures the minimum, over all nonzero input/output difference pairs, of the sum of the input difference's Hamming weight (in some agreed word-granularity, not bit-granularity, for word-oriented designs) and the output difference's Hamming weight — a higher branch number means the diffusion layer more aggressively "spreads" any localized difference across more words, directly feeding the wide-trail/long-trail active-component-counting argument in 1.4 above. Branch number is a *linear-algebra* property of the diffusion layer alone (computable exactly, without any probabilistic/statistical estimation), making it one of the field's cleanest, least-ambiguous diffusion metrics — and correspondingly one of the first things a new design's diffusion layer should be checked against before any more expensive statistical/empirical testing is undertaken.

### 2.4 Entropy growth and information-theoretic diffusion metrics

Some diffusion analyses frame the question information-theoretically: given a fixed input distribution with some entropy deficit (e.g., a single fixed input bit, zero entropy in that position), how many rounds does it take for the *output* distribution's entropy (per bit, or jointly) to approach the maximum-entropy (uniform) distribution expected of a random function — a framing that generalizes SAC/BIC's binary "does it flip" language into a continuous, information-theoretic one, more naturally extensible to multi-bit or algebraic (not just single-bit-flip) input perturbations, though correspondingly more computationally expensive to estimate empirically at real design scale.

### 2.5 Graph-based and structural connectivity metrics

Beyond the state-graph connectivity notion in 1.3, more refined graph-based diffusion metrics track not just *whether* a dependency path exists between an input and output bit after k rounds, but the *number of independent paths* and their *aggregate influence weight* — closer in spirit to how differential/linear trail-counting arguments (1.4/1.5) actually work than simple binary connectivity is, and increasingly the framing automated-search-tool output is interpreted through (a trail search doesn't just tell you connectivity exists; it tells you the *actual probability-weighted* paths, which is strictly more informative).

### 2.6 Differential and linear propagation as diffusion metrics

It's worth stating explicitly, because it's a commonly blurred distinction (flagged again as a named mistake in `08`): **differential and linear trail probability, as computed via the automated-search tooling of `05`, is not merely a "diffusion metric" among several equally-weighted options — it is the actual cryptanalytic-security-relevant quantity**, whereas SAC/BIC/avalanche/branch-number are all *proxies* or *necessary-but-insufficient design-quality indicators* that correlate with, but do not directly measure, resistance to differential/linear cryptanalysis specifically. A design can score excellently on SAC/BIC/avalanche testing while still having an exploitable low-probability-but-nonzero differential trail across its full round count that only a genuine MILP/SAT trail search would surface — **this gap is precisely the most commonly cited "blind spot" of the softer diffusion metrics, and is why no serious current publication can substitute avalanche/SAC/BIC testing for actual automated differential/linear trail search as its primary security evidence** (elaborated further in `08`'s "confusing diffusion with security" named-mistake discussion).

### 2.7 Statistical diffusion testing and visual tools

Beyond the formal SAC/BIC dependency-matrix heatmap (2.1 above), practical diffusion evaluation commonly includes: **avalanche-weight-distribution histograms** (plotting, across many random single-bit-flip trials, the distribution of *how many* output bits flipped — should cluster tightly around n/2 for an n-bit output, with a spread consistent with a binomial distribution, for a well-diffusing design); **round-by-round diffusion progression plots** (tracking the dependency-matrix heatmap's convergence toward the ideal 0.5-everywhere pattern round by round, useful for identifying the *minimum* round count at which full, SAC-compliant diffusion is achieved — directly informing the round-count/performance tradeoff discussed in `02`, §1.1); and, less formally but commonly seen in conference-talk and blog-level design exposition (though generally expected to be backed by the formal metrics above in an actual paper submission), direct **bit-pattern visualizations** of a permutation's state after successive rounds starting from a structured (e.g., single-bit-set) input, giving an intuitive, if not rigorous, visual sense of diffusion speed.

### 2.8 Blind spots, known failures, and historical mistakes — a synthesized list

- **SAC/BIC/avalanche compliance does not imply differential/linear-cryptanalytic security** (2.6 above) — the single most important, most-repeated blind spot in this entire section, and a documented, recurring mistake in independent (non-peer-reviewed) ARX design proposals specifically (elaborated in `08`).
- **Branch number is a property of the linear diffusion layer alone** and says nothing, by itself, about the nonlinear component's (the ARX-box's) own probability distribution — a high branch number combined with a poorly-chosen ARX-box internal structure can still yield a weak overall design; the long-trail strategy's two-part structure (1.4 above) exists precisely because *both* pieces are independently necessary.
- **Round-count sufficiency for SAC/BIC compliance is not the same as round-count sufficiency for the target security level** — a design can achieve full statistical diffusion (SAC/BIC-compliant dependency matrices) in far fewer rounds than are actually needed to defeat the best-known (or best-findable-via-automated-search) differential/linear trail, and using "rounds until SAC-compliant" as a proxy for "rounds needed for security" is a documented historical design mistake (several early, informally-analyzed ARX proposals in the amateur/independent-researcher space have made exactly this substitution, per the pattern discussed in `08`).
- **Empirical dependency-matrix estimation via random sampling has its own statistical-confidence blind spot**: a dependency-matrix entry estimated from, say, 2^20 random trials has real sampling noise, and a design that appears "close enough" to the ideal 0.5 value in a modest-sample-size empirical test can still harbor a small-but-cryptanalytically-relevant bias that only a much larger sample (or, better, an exact analytical computation where tractable) would reveal — a genuine, if narrower, statistical-methodology blind spot directly analogous to the CSPRNG randomness-testing blind spot covered in `06`.
